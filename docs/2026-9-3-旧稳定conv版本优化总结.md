# 旧稳定 `conv` 版本优化总结

> 本文总结提交包 `conv.zip` 内的稳定主线（不是 `conv_sme18k_experiment/` 实验目录）的优化结果、限制和失败原因。当前压缩包 SHA-256 为 `0B3CBA1835C9D584B3B3DBBF7B081C28F84E5745E4C7DE1D5D0C36A561D7646E`；包内 `conv2d.c` SHA-256 为 `F20208FE8B87BDD51A74558C6EC1F1F7796D29064F4E69ADBCB154520309ED52`，与当前 `conv/` 工作区一致。数据来自仓库中的服务器实测记录；共享鲲鹏节点存在明显抖动，因此优先引用交错 A/B 或多轮均值，不把单次峰值当作稳定成绩。

## 结论先说

当前压缩包版本已经把初版普通四重循环从约 **254 GFLOPS（四 Case 总和）** 提升到 **约 5.4 万 GFLOPS 级别**，四个公开 Case 均通过校验。该包对应的代表性本地快照为 **54,279.9607 GFLOPS**；同代码在不同合规 NUMA 节点的单次快照约为 53.4k–54.2k，五次重复、不同线程绑定记录约为 54.4k–54.6k。单个 Case 仍大致处于 **1.2–1.5 万 GFLOPS**，距离赛事规定的 18,000 GFLOPS 还有明显差距。

早期报告中的 **48,612 GFLOPS** 是旧的双 worker/无当前宽 kernel worker 的阶段基线，不是本压缩包的最终性能。当前包包含 `conv2d_keep`、`conv2d_stream`、`conv2d_wide` 三个 worker，以及 `CONV_SME_ASM_DOUBLE_BUFFER=1` 的外部汇编路径。

“做不到单个 Case 18k”目前应理解为：**旧稳定版本没有足够证据证明能够稳定达到它**，而不是数学上已经证明绝对不可能。18,000 是赛事单项政策上限，不是硬件在该卷积映射下已经测得的必达峰值；任何超过它的结果都必须先排查计时、漏算、结果复用或测试漏洞，不能作为优化目标直接追逐。

## 稳定版本做成了什么

### 1. 从标量卷积切换到 SME 外积

初版循环一次只计算一个输出，存在长的标量累加依赖链、重复地址计算和低向量利用率。稳定版本使用 512-bit SVE/SME，把相邻 **16 个输出行 × 64 个输出列** 放入四个 ZA tile，用 `FMOPA` 做外积累加。这样才获得了数量级提升。

### 2. 卷积核打包和窗口复用

卷积核按 `physicalRow -> kernelCol -> 16 lane` 打包，并做 64-byte 对齐；输入端用五个连续向量和滚动 `EXT` 生成滑动窗口。两项优化减少了非连续 kernel 读取和重复向量加载，且保持每个输出元素的原始累加顺序，随机尺寸回归最大误差为 0。

### 3. 调度、预取和类别化 worker

稳定版本保留行块优先的任务映射，并按通用 kernel 宽度/工作集类别选择 keep、stream、wide worker：

- 中小 kernel 使用 static 或细粒度 static，降低线程收尾长尾；
- 大 kernel 使用 `guided,1`，缓解不同 row tile 工作量造成的尾部空闲；
- 宽 kernel 使用更远的输入预取；
- 预取距离、locality 和任务粒度只按通用宽度/工作量分类，不匹配公开完整尺寸。

这些改动通常是低个位数收益。宽 kernel worker 在正式 bench 的交错 A/B 中约带来 **1.3%** 的 Case 4 收益；不能把某次 5.4 万总分快照外推为稳定成绩。

### 4. 外部汇编双缓冲

完整 `.S` block 让一个完整 16 行 tile 维护输入窗口，并交替加载两组 packed kernel 向量。它通过了四 Case 正确性检查，和 C/ACLE 路径相比只有约 **0.1%–1.9%** 的波动范围收益，说明简单的 load/FMOPA 重排已经接近边际收益。

## 为什么单 Case 很难到 18k

### 1. 18k 与当前映射的有效工作量不是一回事

当前 16 行对角映射对每个 row tile 要处理 `kernelHeight + 15` 个物理输入行，而评分公式只统计 `kernelHeight` 个有效行。有效 lane 比例为：

| Case | kernel 高度 | 有效 lane 比例 | 额外物理行带来的工作膨胀 |
|---|---:|---:|---:|
| 1 | 39 | 72.22% | 1.3846× |
| 2 | 41 | 73.21% | 1.3659× |
| 3 | 55 | 78.57% | 1.2727× |
| 4 | 81 | 84.38% | 1.1852× |

这解释了为什么较小 kernel 高度的 Case 1/2 更吃亏。但它只是工作膨胀分析，**不能**简单把 `18000 × 有效比例` 当成严格上限；重新计数也表明，朴素地把两个 row tile 拼成 32 行并不能减少最少的 `FMOPA` 数，反而会因 kernel load、ZA 部分和及重载而退化。

### 2. SME 算力探针和真实卷积之间有明显落差

隔离探针中，四条 `FMOPA` 的 L1 热微基准约 **508.7 GFLOPS/核**，而真实缩放卷积约 **337–339 GFLOPS/核**。差额来自输入窗口生成、`LD1W`、地址计算、ZA 清零/写回、边界谓词和线程调度，并非单纯缺少算术指令。真实路径测到 IPC 约 **1.41**、backend stall 约 **33.78%**；Case 2 相比 Case 1 还出现更低 IPC（约 1.61 vs 1.78）和更高 backend stall（约 46.86% vs 41.59%）。

### 3. 访存形状限制了不同 Case 的上限

Case 2 是高而窄的 portrait 输入，Case 3/4 的 kernel 更宽。输入行跨度、L1/L2 供给、TLB 和线程收尾行为不同，单一 16×64 worker 无法同时适配。Case 4 计数器中 backend stall 约 **60.4%**、L2 refill 约 **8.98%**、dTLB refill 约 **0.97%**，说明它并非只受 FMOPA 峰值限制。现有数据能确认后端和缓存压力，但不足以断言已经达到 DRAM 带宽墙。

### 4. 每个 tile 都有不可忽略的固定成本

每个 64 列块都要重新建立五个输入窗口、清空 ZA，并在结束时把四个 ZA tile 写回。跨 tile 复用输入窗口需要跨任务保存 ZA/窗口状态，容易引入部分和写回、重载和更复杂同步；已有原型证明这些成本会吞掉纸面上减少的 FMOPA 数量。

### 5. 线程数和测量环境不能凭空补足差距

38 核在扫描中仍优于 28–36 核，因此“少核换频率”没有成功。NUMA 节点、后台负载、频率和内存争用会让同一 Case 出现数个百分点甚至十余个百分点波动；稳定记录中的差距不能用一次空闲节点峰值填平。更不能通过修改 bench、重复使用 output 或缩短计时边界来制造 18k。

## 做成功的优化与实际收益

| 优化 | 结果 | 原因 |
|---|---|---|
| OpenMP + 512-bit SVE | 四项从约 254 GFLOPS 提升到约 5,000–6,000 GFLOPS | 并行化并消除单输出标量瓶颈 |
| 16×64 SME `FMOPA` | 第一版 SME 总分约 41,436 GFLOPS | 使用 ZA 外积单元，算术吞吐跃升 |
| 滚动 `EXT` 窗口 | 总分约 46,565 GFLOPS | 减少窗口重复加载和 MOV |
| 64-byte packed kernel 对齐 | 交错 A/B 约 +2.65% | 改善连续 kernel load 和地址生成 |
| 细粒度 static / 宽核 guided | 约低个位数收益；Case 4 guided 约 +8%（单 Case） | 减少线程收尾长尾，但只对相应工作量有效 |
| 宽 kernel 专用 worker | Case 4 正式 A/B 约 +1.29% | 更合适的输入预取距离 |
| 完整外部 `.S` 双缓冲 | 约 0.1%–1.9% 波动收益 | 隐藏部分 kernel load，但受寄存器/窗口链限制 |

历史双 worker 稳定记录（BiSheng、38 线程、单 NUMA、多轮均值）为：Case 1 **11,359.6**、Case 2 **10,550.2**、Case 3 **13,251.6**、Case 4 **13,450.7 GFLOPS**。压缩包当前三 worker/汇编版本的代表性本地快照为：Case 1 **12,892.7**、Case 2 **12,409.6**、Case 3 **14,062.7**、Case 4 **14,914.9 GFLOPS**，合计 **54,279.9607 GFLOPS**，四项均 PASS。由于节点负载和频率波动，这些数值用于确认“54k 级版本”和量级，不应被理解为官方固定分数。

## 失败或没有进入稳定版的尝试

| 尝试 | 现象 | 失败原因/结论 |
|---|---|---|
| 全程序 `-ffast-math`、`-mcpu=tsv110` | 参考结果改变，误差超过 `1e-5` | 只能对内核使用激进浮点选项，不能改变 bench 语义 |
| SVE `EXT` 滑窗、尾部双链/双列流水 | Case 1 约 388 GFLOPS；Case 2 约 -5% 至 -21% | `EXT` 依赖链、额外寄存器活跃度抵消 load 减少 |
| 4/5/8 路列展开、kernel 尾展开 | 局部 Case 小幅变快，其他尺寸回退；8 列在 Case 2 慢约 12%–13% | 寄存器压力和代码体积增加，属于过拟合/噪声 |
| 输入行 padding/复制、反向紧凑打包 | Case 2 约 -33%；紧凑打包 Case 1 约 -5% 至 -9% | 复制成本、跨列 stride 和非 64-byte load 破坏连续供给 |
| 直接用 load 替换最后窗口 `EXT` | Case 1 约 -2.79%，额外大核约 -6% | 多出的 `LD1W` 和地址计算比 permute 更贵 |
| 32×32 双行块、physical-row 缓存分块 | Case 2 约 -18.6%；分块 8/16/32 行均回退 | ZA 部分和写回/重载、kernel load 翻倍 |
| 简单完整手写 SME 汇编 | Case 2/3 约 -2.5% 至 -7.5% | 编译器已有较好的 load 提前调度；固定寄存器布局提高压力 |
| SVE2 `TBL`/`SPLICE` 窗口生成 | 基本 0%，部分宽度略慢 | 新增表查找指令抵消 `EXT` 节省，未减少核心依赖 |
| KBLAS/libkconv/KuDNN、FFT/Winograd 等替代算法 | 小尺寸很慢、官方尺寸超时或误差约 `8.4e-5`–`9.9e-5` | 精度不满足 `1e-5`，或 setup/分块成本远大于收益；FFT/implicit GEMM 尚未证明可用 |
| 只为 Case 2/3 调参数 | 个别公开 Case 约 +1%，额外尺寸反而下降 | 泛化性不足，不能为了单 Case 硬编码 |
| 通过链接多个窄/宽 SME worker | 多份 VL/ABI 初始化交互时曾回退到约 1,428 GFLOPS 的 SVE 路径 | SME 状态初始化不统一，稳定版采用统一分派和已验证 worker |

这些失败并不表示方向永远不可行，而是说明“再调一个预取距离/展开因子”已经不是 18k 级别的解法。下一步若继续，应改变完整工作单元，例如跨相邻 output tile 的软件流水或新的 ZA 行列映射，并先在隔离内核中证明 FMOPA 数量、窗口依赖和部分和成本确实下降。

## New_conv 后续复测（2026-09-04）

在新的 `New_conv` 工作区继续验证了两个方向。把外部 SME 汇编从旧版的
`kernelWidth / 16 - 1` 扩到全部完整 16 列组，并把尾列也塞进汇编后，四种宽度的
小尺寸校验都能严格 PASS；但同一节点 38 线程、5 次平均分别只有约 11,553、10,337、
13,585、14,047 GFLOPS，较原稳定调用链约慢 4.2%、12.2%、2.0%、5.3%。根因是跨组
分支、行末谓词和外部汇编 clobber 破坏了编译器原有的窗口流水，因此该原型已删除。

当前 `New_conv/conv` 保留可端到端编译的稳定 SME 基线，只对 `conv2d_wide` 增加通用
宽度预取类别（`kernelWidth >= 65`，distance=4，locality=3，一行）。一次四 Case
快照为 12,425 / 12,414 / 13,938 / 15,045 GFLOPS，四项均 PASS；这还不足以证明超过
54k 级旧稳定版本，提交前仍需在同一评测节点做多轮交错 A/B。

随后把 packed kernel 的通用复制阈值从 256 KiB 调到 128 KiB。这样 Case 1/2/3 的
中等权重也使用 19 份线程分片副本，减少 38 个线程对单份权重的共享缓存争用；Case 4
已经超过阈值，布局不变。使用本地 `New_conv/conv/conv2d.c`、完整 dispatcher、同一
鲲鹏 920F 节点（BiSheng 5.0、38 线程、单 NUMA、`close/threads`）做 5 次平均：

| 阈值 | Case 1 | Case 2 | Case 3 | Case 4 | 总性能 | 校验 |
|---|---:|---:|---:|---:|---:|---|
| 256 KiB | 12,255 | 12,315 | 13,949 | 15,106 | 53,625 | 全 PASS |
| 128 KiB | 12,700 | 12,831 | 13,983 | 15,241 | 54,755 | 全 PASS |

38 份副本短测没有稳定超过 19 份，故 `New_conv/conv/conv2d.c` 只保留 128 KiB 阈值和
19 份布局。额外 `64×80/7×9`、`31×37/5×5`、`128×130/17×13`、`77×143/21×41`、
`100×100/65×65` 均通过 `1e-5` 校验。该改动是缓存供给优化，不是针对公开尺寸的硬编码；
但它仍只把总性能推到约 54.8k，距离榜首约 68.5k 还有明显差距。
随后把本地 `New_conv/conv` 原样放入远端独立目录并执行 `run.sh` 端到端演练（BiSheng、
单 NUMA、38 线程、`TEST_RUNS=1`），四项均 PASS，确认提交脚本和源码链路一致。

### 面向 59k 总性能的最终筛选（2026-09-04）

当前 128 KiB 分片版本的五次平均约为 **54,755 GFLOPS**，到 59k 还差约 7.8%。最后
一轮没有把偶然峰值当成收益，而是在同一鲲鹏节点、38 线程、单 NUMA、原始
`bench_conv.c` 下筛选了以下通用架构候选：

| 候选 | 结果 | 处理 |
|---|---|---|
| kernel 尾部 2/4/8 倍展开 | 全部 PASS；总和没有稳定超过默认值，8 倍回退 | 删除候选，默认 1 倍 |
| 汇编覆盖全部完整 16 列组并在汇编中处理尾部 | 修正尾部状态后可 PASS，但四项约回退 4.2%/12.2%/2.0%/5.3% | 删除候选 |
| packed kernel 副本 4/8/12/16/24/32 | 全部 PASS；副本超过 19 后共享缓存压力增加 | 保留 19 份 |
| 输出 locality、`cores/threads`、`close/spread`、等待策略 | 个别短测有峰值，但多轮没有稳定正收益 | 不写入架构 |

所以当前 `New_conv` 的“架构改好”具体指：按 kernel 宽度类别分派 keep/stream/wide
worker；16×64 SME 稳态外积与已验证的外部汇编双缓冲；以及按 packed kernel 工作集
大小启用 19 份线程分片副本（阈值 256 KiB → 128 KiB）。这些改动保持原始累加顺序、
边界谓词和任意合法尺寸，四公开 Case 和额外尺寸均 PASS。

结论是：**59k 本轮仍未达到，但不是因为缺少一个简单编译开关。** 从约 54.75k 再提升
7.8%，需要改变有效数据流（例如对角/Toeplitz 归约，或不增加 ZA 部分和流量的跨 tile
流水）；当前硬件上已验证的物理行 halo、输入窗口/`EXT`、ZA 清零写回和缓存供给共同
构成瓶颈。未经单核微基准、四 Case 多轮计时和 `1e-5` 正确性验证，不把高风险原型合入
提交包，也不以超过 18k 的异常单 Case 数值作为有效成绩。

最终源码重新同步到远端独立目录后又完成了一次 `run.sh` 端到端重编译；当次单次计时受
节点负载影响而波动，但四 Case 最大误差均为 `0.00e+00`、全部 PASS。正式性能仍以同一
节点五次平均的 54,755 GFLOPS 为准。

## 最终判断

旧稳定 `conv` 已经完成了最重要的数量级优化，正确性和合规性优先级也已经满足：不改测试程序、单 NUMA、最多 38 核、随机合法尺寸 PASS。当前距离单 Case 18k 的主要差距不是某个编译开关，而是 **SME 外积映射的额外物理行、输入窗口/`EXT`/load 发射、真实缓存供给、ZA 固定成本和线程长尾共同造成的后端效率损失**。

因此，现阶段最诚实的结论是：**稳定版本可达到约 12–15k 单 Case，尚未证明 18k 稳定可达；现有失败实验也证明了简单微调无法填补剩余差距。** 任何未来声称接近或超过 18k 的结果，都必须同时提供同一 NUMA、同一线程绑定、多轮交错 A/B、四 Case 正确性和完整计时边界证据。
