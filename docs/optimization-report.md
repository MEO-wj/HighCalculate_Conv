Case 3 和 Case 4 已越过 70% 阶段线；Case 1/2 尚未达到 12600 GFLOPS。70% 不是优化终点，后续仍向 80%、90% 以及合规范围内尽可能接近 100% 推进。当前四项占比分别为 63.11%、58.61%、73.62% 和 74.73%。

## 2. 合规边界

本轮优化始终遵守以下边界：

- 未修改 `conv/bench_conv.c`，并已确认它与 `conv_init/bench_conv.c` 字节内容一致；
- 未修改 `conv_init/` 中的任何初版文件；
- 只使用单一 NUMA 节点和最多 38 个 CPU 核心；
- 没有使用 GPU、跨 NUMA、结果缓存、漏算、伪造计时或测试程序漏洞；
- 没有针对四个公开尺寸直接返回特制结果；
- 每次 `conv2d` 调用都重新完成完整 direct convolution；
- 所有优化路径均保留合法尺寸、非方卷积核和尾块处理；
- 没有读取或复制其他参赛队伍的核心实现。

当前实现改变的是计算组织、向量/矩阵指令、数据布局、缓存预取和线程调度，不改变卷积定义或接口。

## 3. 原始计算及主要瓶颈

二维 valid convolution 为：

```text
output[j, i] = Σjk Σik input[j + jk, i + ik] × kernel[jk, ik]
```

输出尺寸为：

```text
outputHeight = inputHeight - kernelHeight + 1
outputWidth  = inputWidth  - kernelWidth  + 1
```

初版为 `j → i → jk → ik` 四重循环。它一次只更新一个输出，最内层反复读写同一输出元素，存在很长的浮点累加依赖链，地址计算较多，也难以利用 512 位 SVE 和 SME 矩阵外积单元。

## 4. 当前 SME 算法

### 4.1 把相邻输出行改写成外积

当前微内核同时计算 16 个相邻输出行和 64 个相邻输出列。对于某个物理输入行和卷积核列：

- 一个 16-lane 向量保存 16 个输出行各自对应的卷积核系数；
- 一个 16-lane 向量保存 16 个相邻输出列的输入值；
- 一条 SME `FMOPA` 将两个向量做外积并累加到一个 16×16 ZA tile；
- 同时使用 4 个 ZA tile，覆盖 16×64 输出块。

这正好把原本大量标量乘加映射到鲲鹏 CPU 的 SME 矩阵流水线。每个输出元素内部仍按物理行和卷积核列的确定次序累加，官方四项实测最大误差为 0。

### 4.2 卷积核打包

调用开始时将卷积核打包为适合 SME 的连续向量：

```text
packed[physicalRow][kernelCol][outputRowLane]
```

无效的顶部和底部行 lane 填 0。打包缓冲区按 64 字节边界对齐，每次调用重新生成并在结束时释放，不跨调用缓存结果。其大小天然为 64 字节整数倍。两轮交错 A/B 中，对齐使四项总分稳定提升约 2.65%；公开最大卷积核下缓冲区约为数百 KiB，能够明显改善连续加载和地址生成。

### 4.3 SVE 滑动窗口复用

卷积核列每 16 列为一组。每组从 5 个连续输入向量开始，通过 15 次逐 lane 滚动的 SVE `EXT` 生成右移窗口，供 4 个 ZA tile 复用。与直接为每个偏移生成 `EXT(input0,input1,shift)` 相比，滚动形式把热循环中的向量 `MOV` 静态计数从 77 条降到 22 条；相邻 16 列组还继续携带 4 个窗口，只加载一个新的末端向量。该变化保持每个输出元素的累加顺序，四个官方 Case 最大误差仍为 0。

### 4.4 缓存和写回

- 在最后若干物理输入行中分批预取即将写回的输出缓存行；
- 对 41–64 宽的中等卷积核每步预取两行，其他宽度每步预取一行；
- 39/41/55 宽卷积核把每个行块拆成 4 个列任务，较宽卷积核拆成 2 个列任务，在负载均衡和顺序缓存局部性间折中；
- 完整 64 列块直接从 4 个 ZA tile 写回，宽度尾部使用谓词化 SME 路径。

这些选择基于宽度区间和通用工作量，不是对四组完整公开尺寸进行硬编码。

### 4.5 兼容回退

如果编译器或 CPU 没有 SME，代码仍保留显式 SVE 路径；若连 SVE 也不可用，则回退到通用 OpenMP/SIMD 实现。GCC 12 当前不提供本实现使用的 SME ACLE，因此 `run.sh` 的 GCC 模式会显式关闭 SME；正式性能路线默认使用 BiSheng。

## 5. 编译与运行配置

服务器关键环境：

```text
架构：AArch64

每个 NUMA 节点：38 核

编译器：BiSheng Enterprise 5.0.0.2，Clang 19.1.7
默认测试节点：NUMA 7
```

运行方式：

```sh
cd conv
NUMA_NODE=7 COMPILER=bisheng bash run.sh
```

`bench_conv.c` 和 `conv2d.c` 分开编译：

```text
bench_conv.c：-O3 -mcpu=native -msve-vector-bits=512 -fopenmp
conv2d.c：    -O3 -ffast-math -funroll-loops -falign-loops=32
             -fno-plt -fomit-frame-pointer -mcpu=native
             -msve-vector-bits=512 -fopenmp
```

`-ffast-math` 只作用于参赛内核。若对测试程序也启用该选项，参考实现会改变浮点累加行为并导致校验失败，因此测试程序必须保持严格编译。

OpenMP 配置为：

```text
OMP_NUM_THREADS=38
OMP_DYNAMIC=false
OMP_PROC_BIND=close
OMP_PLACES=cores
numactl -N 7
```

## 10. 后续最有价值的优化方向

1. 使用独立诊断 harness 隔离 `conv2d` 的性能计数器；直接统计官方程序会被慢速参考卷积淹没；
2. 导出最终 SME 热循环汇编，检查 `FMOPA` 间隔、SVE spill、寄存器分配和加载调度；
3. 尝试手写双 kernel 寄存器软件流水，在不超过误差阈值的前提下交错加载、`EXT` 和 `FMOPA`；
4. 研究保持 SME 外积密度的跨 row-tile 边缘合并；已证明逐行 SVE 边缘不可行；
5. 在完成 64 字节对齐后，继续扫描 packed physical-row padding、L1 组冲突和输出预取距离；
6. 定位 Case 2 的 L1/L2/TLB 或线程长尾问题；
7. 在 NUMA 5、7 等低负载节点重复 A/B，而不是依据实时榜单或单次峰值判断。

任何后续方案仍必须遵守：正确性 PASS、泛化、单 NUMA、最多 38 核、不得修改测试程序，以及单 Case 不超过 18000 GFLOPS。

## 11. 为什么到 90% 必须改变计算映射

当前 16 行 SME 对角映射每个 row tile 要执行 `kernelHeight + 15` 个物理行，而计分只统计 `kernelHeight` 个有效行。保持当前映射时，按官方单项 18000 上限估算的结构上限为：

| Case | 当前占比 | 当前映射近似结构上限 | 去掉额外 15 行且保持现有效率时 |
|---|---:|---:|---:|
| Case 1 | 63.11% | 72.22% | 87.38% |
| Case 2 | 58.61% | 73.21% | 80.06% |
| Case 3 | 73.62% | 78.57% | 93.70% |
| Case 4 | 74.73% | 84.38% | 88.56% |
| 总计 | 67.52% | 约 77.10% | 约 87.42% |

因此当前结构下，即使把 SME 稳态循环推到理想满载，总体也很难超过约 77%。可信的 90% 路线需要两部分同时成立：

1. 用跨 tile 边缘合并、动态有效 lane 压缩或新的 implicit-Toeplitz 映射，消除大部分 `+15` 额外外积，同时保持 `FMOPA` 的计算密度；
2. 再通过汇编流水、packed 布局、缓存/TLB 和线程长尾优化，将消除边缘后的约 87.42% 推高至少约 3%。

接近 100% 还要求 Case 2 的等效利用率从约 80% 明显提高。FFT、implicit GEMM 等数学替代路线只有在随机数据误差稳定不超过 `1e-5`、不超过单项 18000、且获得官方规则允许时才值得进入性能实现。详细推导、各缓存/数学/核心/指令方向和实验退出条件见 `docs/2026-08-27-Conv高性能计算优化流程和结论.md` 的第 7–8 节。
