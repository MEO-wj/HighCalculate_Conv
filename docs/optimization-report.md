# CONV 优化工作与性能测试报告

> 更新时间：2026-08-27  
> 赛题：鲲鹏高性能计算全球挑战赛（S2 赛季）CONV 优化赛题

## 1. 报告目的

本文档总结当前仓库已经完成的整理、代码优化、正确性修复和性能测试工作，并记录本地 x86 环境与官方鲲鹏 AArch64 环境下的测量结果。

不同硬件环境的 GFLOPS 不能直接用于计算代码加速比。因此，本文只在相同机器、相同编译器和相同线程配置下比较加速效果，并将官方理论上限占比限定为官方鲲鹏服务器实测结果。

## 3. 合规边界

本轮优化没有使用以下手段：

- GPU、CUDA、OpenCL 或其他加速卡；
- 缓存首次计算结果或跳过后续调用；
- 修改 `conv/bench_conv.c`；
- 修改 `conv_init/` 中的初版文件；
- 针对四个公开输入尺寸返回特制结果；
- FFT、FP16、BF16 或不满足精度要求的近似计算；
- 修改计时逻辑、伪造耗时或伪造 GFLOPS；
- 超出单 NUMA 节点或 38 个 CPU 核心。

每次 `conv2d` 调用都会重新完成完整卷积计算。当前实现仍是通用 direct convolution，只改变了循环组织、向量化方式、寄存器/缓存使用和线程配置。

## 4. 核心代码优化

### 4.1 原始计算方式

原始实现一次只计算一个输出元素：

```text
输出行 j
  输出列 i
    卷积核行 jk
      卷积核列 ik
        output[j,i] += input[j+jk,i+ik] × kernel[jk,ik]
```

这种结构存在单条很长的浮点累加依赖链，并且不利于编译器进行高效 SIMD。

### 4.2 当前计算方式

当前实现一次计算一个相邻输出块：

```text
输出行 j
  输出列块 i ... i+block-1
    为块内每个输出建立独立累加器
    卷积核行 jk
      卷积核列 ik
        使用 SIMD 同时更新多个不同输出
    将整个输出块写回内存
```

向量 lane 分别对应不同输出元素，因此每个输出内部仍严格按照 `jk → ik` 的原始顺序累加，不需要水平归约，也没有拆分同一个输出的部分和。

### 4.3 具体方法

- 使用相邻输出分块增加独立累加链；
- 使用 `#pragma omp simd` 跨输出列向量化；
- 使用行指针消除内层二维索引乘法；
- 使用 `__restrict__` 声明输入、卷积核和输出不重叠；
- 使用零初始化累加器直接生成输出，删除全量输出 `memset`；
- 使用 `schedule(static)` 分配输出行；
- 保留与参考实现一致的标量尾部；
- 在官方环境启用 512 位 SVE 和循环展开；
- 在官方环境将输出块调整为 80。

## 5. 正确性验证

验证覆盖：

- 四个官方测试尺寸；
- 非方形卷积核；
- 输出宽度小于一个向量块；
- 输出宽度不能被块大小整除的尾部；
- 1、2、7、38 等不同线程数；
- 本地 x86 和官方 AArch64 两种架构。

官方鲲鹏环境最终四个用例均得到：

```text
校验：PASS
最大误差：0.00e+00
```

首次 ARM 测试曾发现标量尾部由于编译器浮点融合方式不同而产生约 `9.16e-5` 最大误差。恢复为与参考实现相同的内存逐项累加后，误差降为零。

## 6. 本地同环境性能提升

测试环境为本地 Windows x86_64、GCC 8.1、OpenMP 38 线程。每个 Case 正式计时三次取平均。

| Case | 原始 GFLOPS | 通用 SIMD GFLOPS | 加速比 |
|---|---:|---:|---:|
| Case 1 | 30.0939 | 281.9518 | 9.37× |
| Case 2 | 29.6882 | 250.7103 | 8.44× |
| Case 3 | 30.7042 | 270.4103 | 8.81× |
| Case 4 | 46.6147 | 202.4426 | 4.34× |
| 总计 | **137.1010** | **1005.5150** | **7.33×** |

本地总性能增加：

```text
1005.5150 - 137.1010 = 868.4140 GFLOPS
```

本地相对性能提升：

```text
(1005.5150 ÷ 137.1010 - 1) × 100% ≈ 633.4%
```

该组通用 SIMD 数据来自 ARM 尾部修复前的本地版本，但该版本在 x86 上最大误差为零。尾部仅覆盖每行不足一个完整块的输出，最终正式结果仍应以官方鲲鹏环境为准。

## 7. 官方鲲鹏服务器环境

服务器环境信息：

```text
架构：AArch64
CPU 厂商：HiSilicon

每个 NUMA 节点：38 核
SVE 默认向量长度：512 位

```

服务器支持 NEON、SVE、SVE2 和 SME。当前版本使用 CPU 和 SVE，不使用 GPU。

## 8. 官方环境编译与运行配置

当前最佳复现配置已写入 `conv/run.sh`：

```sh
gcc -O3 -mcpu=native -msve-vector-bits=512 -funroll-loops \
    -DCONV_OUTPUT_BLOCK=80 \
    bench_conv.c conv2d.c -o conv2d_test -lm -fopenmp
```

OpenMP 与 NUMA 配置：

```text
OMP_NUM_THREADS=38
OMP_DYNAMIC=false
OMP_PROC_BIND=close
OMP_PLACES=cores
numactl -N 1
```

## 9. 官方环境 SVE 调优收益

同一台鲲鹏服务器、相同源码的两种编译配置：

| 配置 | 向量方式 | 输出块 | 总 GFLOPS |
|---|---|---:|---:|
| 默认 GCC `-O3` | 128 位 NEON | 32 | 2563.9538 |
| 当前最佳配置 | 512 位 SVE | 80 | 5030.4209 |

SVE 调优增加：

```text
5030.4209 - 2563.9538 = 2466.4671 GFLOPS
```

加速比与相对提升：

```text
5030.4209 ÷ 2563.9538 ≈ 1.962×
(1.962 - 1) × 100% ≈ 96.2%
```

该比较只代表当前优化源码从默认 NEON 编译到 SVE 调优编译的收益，不代表原始四重循环到最终版本的官方服务器加速比。

## 10. 最终官方服务器结果

最终结果来自 `conv/run.sh` 的完整端到端执行：

| Case | 耗时 | GFLOPS | 最大误差 | 单 Case 上限 | 上限占比 |
|---|---:|---:|---:|---:|---:|
| Case 1 | 57.21 ms | 1317.4434 | 0 | 18000 | 7.32% |
| Case 2 | 86.28 ms | 964.7403 | 0 | 18000 | 5.36% |
| Case 3 | 116.82 ms | 1378.7988 | 0 | 18000 | 7.66% |
| Case 4 | 252.49 ms | 1369.4384 | 0 | 18000 | 7.61% |
| 总计 | — | **5030.4209** | — | **72000** | **6.99%** |

理论总上限：

```text
18000 × 4 = 72000
```

当前理论上限利用率：

```text
5030.4209 ÷ 72000 × 100% ≈ 6.99%
```

距离理论总上限：

```text
72000 - 5030.4209 = 66969.5791 GFLOPS
```

理论剩余空间约为 `93.01%`。

服务器为共享环境，测试时有其他在线用户和系统负载。多次测试的总分约在 `4965–5030`，最终端到端结果位于该稳定区间内。

## 11. 数据口径限制

目前可以严格确认两段同环境提升：

```text
本地原始代码 → 本地通用 SIMD：
137.1010 → 1005.5150 GFLOPS
7.33×，提升约 633.4%

官方服务器当前源码 NEON → 官方服务器当前源码 SVE：
2563.9538 → 5030.4209 GFLOPS
1.962×，提升约 96.2%
```

不能直接将本地原始 `137.1010` 与官方服务器最终 `5030.4209` 计算为代码加速比，因为两者使用不同 CPU、指令集和编译器。

当前尚未在官方服务器运行 `conv_init/conv2d.c`，所以“官方服务器原始四重循环 → 最终 SVE 版本”的准确加速比仍待补测。

## 12. 后续优化方向

当前实现距离单 Case `18000 GFLOPS` 理论上限仍有较大空间，后续优先考虑：

1. 编写显式 AArch64 SVE 微内核，减少对编译器自动向量化的依赖；
2. 检查汇编中的累加器寄存器分配和栈溢出；
3. 对卷积核列按 2 或 4 展开，同时保持原始累加顺序；
4. 使用 SVE 向量拼接复用相邻滑动窗口输入；
5. 根据输出宽度余数通用选择 64 或 80 输出块，减少标量尾部；
6. 测试一行与两行输出微内核的缓存复用；
7. 继续比较 GCC 与毕昇编译器；
8. 在低负载官方节点重复测试并记录性能计数器；
9. 在获得明确授权后补测官方服务器原始四重循环基线。

所有后续优化仍必须遵守正确性、泛化、单 NUMA、最多 38 核和单 Case `18000 GFLOPS` 上限要求。
