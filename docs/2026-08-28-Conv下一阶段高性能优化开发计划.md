# Conv 下一阶段高性能优化开发计划

> 制定时间：2026-08-28 18:16 CST
> 适用对象：鲲鹏高性能计算全球挑战赛 S2 CONV 优化赛题
> 当前候选：`conv/conv2d.c` SHA-256 `26c606f306eb91dd36ced1d1e30c803ee2000a9a93d258d096724a0e277c9f02`
> 性能对照基线：加入 SME VL 安全化前 SHA-256 `2b3df128275588060ae646a271fc8fadcf2b75bdbfa563ca1fcb9e98247af6e7`

## 1. 文档目的

本计划用于指导下一阶段 Conv 性能开发，目标不是继续堆叠零散宏参数，而是建立一条可以验证、可以回退、符合赛事规则的结构化优化路线。

计划的第一阶段目标是把官方总性能从当前 `49667.4161 GFLOPS` 提升到 `57600 GFLOPS` 左右，即达到四项理论总上限 `72000 GFLOPS` 的 80%。第二阶段在第一阶段真实达成后，再评估冲击 `64800 GFLOPS`、即 90% 理论总上限的可行性。

必须诚实区分“目标”和“已经证明可以达到的结果”：现有硬件数据证明仍有计算空间，榜单也证明规则范围内存在更高性能实现；但任何具体提升都必须经过本计划的正确性、泛化性和重复性能门槛，不能预先承诺尚未测出的 90%。

## 3. 必须遵守的边界

所有阶段均必须满足：

1. 不修改、替换或格式化 `conv/bench_conv.c`；
2. 不修改 `conv_init/` 中的官方初版文件；
3. 不改变 `conv2d` 的函数签名、输出语义和 valid convolution 定义；
4. 不缓存上一次调用的结果，不复用测试输出，不绕过任何计算；
5. 不按公开的完整 rows、cols、kernel_rows、kernel_cols 组合进行硬编码；
6. 随机数据和额外合法尺寸必须正确，绝对误差必须不超过 `1e-5`；
7. 只使用一个 NUMA 节点，OpenMP 线程数不超过 38；
8. 不依赖官方节点没有保证提供的管理员权限、大页设置或额外硬件；
9. 任一单 Case 超过 `18000 GFLOPS` 必须先按异常处理，不得直接作为有效结果；
10. 失败实验不得长期隐藏在默认关闭的宏后进入最终提交源码。

如需新增 `conv2d_sme.S` 等源文件，必须先确认官方提交允许包内包含额外源文件；若规则只接受 `conv2d.c`，则使用一个完整、受控的汇编函数块保存在 `conv2d.c` 内，不能修改测试器规避构建要求。

## 4. 可靠测量协议

大幅优化最容易被共享服务器波动误导，因此先统一测试协议。

### 4.1 三层测试

| 层级 | 用途 | 配置 | 是否作为最终成绩 |
|---|---|---|---|
| L1：固定单 CPU | 判断微内核本身 | `OMP_NUM_THREADS=1`，绑定一个 CPU 和其所在 NUMA | 否，只判断代码方向 |
| L2：38 核隔离 harness | 判断并行、缓存和长尾 | 单 NUMA、38 核、连续多次调用 | 是，作为候选筛选 |
| L3：原始 `bench_conv.c` | 正确性与最终 GFLOPS | 官方四 Case，严格参考实现 | 是，最终验收 |

### 4.2 A/B 顺序

每个候选使用同一编译器、同一节点、同一线程绑定和同一参数，采用至少 7 轮交错顺序：

```text
A B B A / B A A B
```

同时记录中位数、最小值、最大值和 MAD。不得只取最好的一次，也不得用不同节点、不同时段的峰值计算代码加速比。

### 4.3 cycle-normalized 指标

除 GFLOPS 外，每个核心候选至少记录：

- cycles；
- instructions 与 IPC；
- frontend/backend stalled cycles；
- L1D access/refill；
- L2D access/refill；
- DTLB refill；
- 每个线程的任务数和最后完成时刻；
- 热循环静态 `FMOPA`、`EXT/TBL`、`LD1W`、`MOV` 和分支数量。

共享负载导致频率或时间变化时，优先用每个完整 16 kernel 列组的 cycles 判断内核是否真实改善。

### 4.4 候选保留门槛

微内核候选只有同时满足以下条件才允许进入主线：

1. 固定 CPU 上至少三个 kernel 宽度类别的 cycles 中位数改善 `>= 3%`；
2. 38 核官方四 Case 总分同期改善 `>= 2%`，或者目标 Case 改善 `>= 4%` 且其他 Case 无超过 `1%` 的稳定回退；
3. 所有官方和额外尺寸 PASS；
4. 没有越界、数据竞争、未定义行为和单 Case 超过 18000 的异常；
5. 提升可以由汇编、缓存事件或线程长尾中的至少一种证据解释。

不足门槛的候选记录到实验文档后删除，不与其他不确定候选叠加。

## 5. 总体技术路线

```text
冻结基线
  ↓
建立固定核周期模型和逐线程画像
  ↓
完整 SME 稳态微内核流水
  ↓
通用 kernel 类别与尾部微内核
  ↓
38 核显式任务区间和长尾消除
  ↓
packed-kernel / L1-L2 联合供给
  ↓
编译、链接、运行时收尾
  ↓
组合回归与干净提交包验证
```

计划把“可能带来较大提升”的工作放在前三个核心阶段。普通预取、参数扫描和编译选项只作为最后的低风险收尾，不能承担 80% 目标。

## 6. 阶段 P0：冻结和复现基线

### P0-1 冻结代码和二进制信息

- 记录 `conv2d.c` SHA-256；
- 记录 BiSheng、GCC、OpenMP runtime 的版本；
- 保存完整 CFLAGS、链接参数、线程环境变量和 NUMA 节点；
- 导出 `conv2d_sme_worker` 的反汇编；
- 记录四 Case 官方 GFLOPS 和固定 CPU 周期。

### P0-2 建立正确性矩阵

除官方四 Case 外，至少覆盖：

| 类型 | 示例 |
|---|---|
| 小型非对齐 | `79×83 / 17×19` |
| kernel 小于 16 | `257×263 / 13×15` |
| kernel 恰好跨 16 边界 | `1024×1537 / 31×33` |
| 中核转置长宽 | `1537×1024 / 43×37` |
| 非公开中核 | `2049×3073 / 53×57` |
| 大核非公开尾部 | `3073×2049 / 73×77` |
| 输出不足一个向量 | 合法的小 outputWidth/outputHeight |
| 退化合法核 | `1×1`、`1×N`、`N×1` |

额外 harness 只用于诊断，不进入提交包，不替代原始测试器。

### P0 完成标准

- 基线四 Case 和额外矩阵全部 PASS；
- 同一低负载节点 7 轮中位数波动可以量化；
- 任何后续结果都能回到该版本。

## 7. 阶段 P1：建立周期模型和逐线程画像

### P1-1 拆分稳态成本

分别测量：

1. 纯 ZA0～ZA3 `FMOPA` 峰值；
2. `FMOPA + kernel LD1W`；
3. `FMOPA + kernel LD1W + 输入窗口 EXT`；
4. L1 热数组上的完整 physical-row 内核；
5. 真实 packed-kernel 和 input 地址流；
6. 加入 OpenMP 任务后的 38 核路径。

每层使用相同有效 FLOP 定义，输出 cycles/16-kernel-column-group。通过相邻两层的增量判断主要损失来自 load、permute、L1/L2 还是线程调度。

### P1-2 逐线程结束时间

在独立诊断版本中记录每个线程：

```text
thread_id
first_task_time
last_task_time
full_blocks
tail_blocks
row_tiles
estimated_work = blocks × physicalRows × kernelWidth
```

诊断代码不得修改 `bench_conv.c`，也不得进入最终性能二进制。若最慢线程相对中位线程长 `>= 5%`，进入 P4 的显式区间设计；否则停止继续扫描 OpenMP chunk。

### P1-3 热循环依赖图

为一个 16 列组标注：

- 每个 z/p/ZA 寄存器用途；
- kernel load 到首次 `FMOPA` 的距离；
- 每个 `EXT` 的来源和消费者；
- 同一 ZA tile 两次 `FMOPA` 的间隔；
- 编译器生成的多余 `MOV`；
- 指针更新和分支位置。

### P1 完成标准

- 能用 cycles 解释固定核实际 GFLOPS；
- 能明确指出至少一个占总周期 `>= 5%` 的可优化关键路径；
- 若没有这样的关键路径，不进入盲目汇编，转到 P5 的新映射计数模型。

## 8. 阶段 P2：完整 SME 稳态汇编微内核

这是第一条可能提供较大增量的主线。以前的逐条内联汇编和固定寄存器 16 列块失败，原因是编译器无法跨多个 `asm volatile` 联合调度。本阶段必须一次接管完整稳态循环，而不是再次逐条替换 intrinsic。

### P2-1 定义微内核边界

汇编只负责满足以下条件的完整块：

```text
16 个输出行 × 64 个输出列
kernelWidth 中的完整 16 列组
activeRows == 16
activeCols == 16
```

行尾、列尾、kernelWidth 尾部和非 SME 机器继续走现有 ACLE/SVE/C 路径。这样把正确性风险限制在稳态块，不牺牲泛化能力。

### P2-2 ASM0：机器码等价版本

- 固定 ZA0～ZA3；
- 固定 5 个输入窗口寄存器；
- 使用两个 kernel 向量寄存器作为双缓冲；
- 明确 predicate 和临时寄存器；
- 保持 kernel 列严格递增的累加顺序；
- 先生成与 ACLE 语义相同的版本，不追求性能。

ASM0 必须完成：

- 官方和额外尺寸 PASS；
- AddressSanitizer 可运行的小尺寸路径无越界；
- 反汇编不存在意外函数调用、SVE spill 和循环内栈访问；
- 固定核性能不比 ACLE 回退超过 3%。

### P2-3 ASM1：双 kernel load 流水

构造两级流水：

```text
K[n+1] LD1W
W[n] EXT / window ready
K[n] × W[n] → ZA0/1/2/3
pointer advance
```

目标是把下一 kernel load 的 load-use latency 隐藏在当前四条 `FMOPA` 和窗口生成之间。每次只改变一种发射顺序，导出机器码并记录每组 cycles。

搜索变量只能是汇编调度，不是公开 Case 参数：

- kernel load 提前 1 或 2 个窗口；
- ZA 发射顺序 `0,1,2,3` 或交错顺序；
- `EXT` 放在相邻 ZA 更新之间或之前；
- 两个 8-vector kernel 基址或一个递增指针；
- 每次展开 8 或 16 kernel 列。

### P2-4 ASM2：跨 16 列组 carry

保留当前已验证的跨组输入窗口携带，只在确实有下一完整组时加载新的末端窗口。不得读取 kernelWidth 之外的 lane，也不得假设公开 kernel 宽度。

### P2-5 汇编候选验收

| 指标 | 最低要求 |
|---|---:|
| 固定核 cycles/组 | 至少降低 5% |
| Case 1/2 固定核中位数 | 均不回退，至少一个提升 5% |
| 38 核四 Case总分 | 同期提升至少 3% |
| 额外尺寸 | 全部 PASS |

若 ASM1/ASM2 都不能比 ACLE 降低至少 3% cycles，则停止外部汇编，不继续扩大代码；这说明硬件乱序已经完成主要调度。

### P2 预期贡献

可信目标为总分 `+4%～+10%`。上限取决于 P1 证明的 load/permute 关键路径；不得把 10% 与其他阶段简单相加。

## 9. 阶段 P3：通用 kernel 类别与尾部专用微内核

Case 2 的 9 列尾部占比明显，而普通双列流水已经失败。本阶段不重新尝试同一种方案，而是让完整组和尾部共享同一 kernel 双缓冲及发射流水。

### P3-1 分派维度

只允许使用通用属性：

```text
fullGroups = kernelWidth / 16
tail = kernelWidth % 16
kernelWidth class: <=16, 17..32, 33..64, >64
output full block count
active row/column predicates
```

尾部按范围生成四类通用模板：

- tail 1～3；
- tail 4～7；
- tail 8～11；
- tail 12～15。

不得只为 tail 1、7、9 或公开 kernelWidth 写孤立路径。每类模板必须在该范围内至少测试三个非公开宽度。

### P3-2 宏模板或代码生成

用宏生成相同结构但不同展开长度的内部函数，避免运行时在每一列判断：

```text
TAIL_KERNEL_1_3
TAIL_KERNEL_4_7
TAIL_KERNEL_8_11
TAIL_KERNEL_12_15
```

模板需要：

- 保持原始列累加顺序；
- 只加载实际存在的 kernel 向量；
- 输入尾部使用安全谓词；
- 控制代码尺寸，避免四个模板污染稳态指令缓存；
- 用反汇编确认没有比普通循环更多的 `MOV` 和 spill。

### P3-3 完整组与尾部统一流水

最后一个完整组在处理后半段时，提前准备尾部的第一个 kernel/input，不另外启动一个寄存器压力很高的双列循环。该方案与本轮失败的“尾部一次提前两列、常驻八个输入向量”不同：只允许一个下一 kernel 和一组下一输入窗口处于飞行状态。

### P3 验收标准

- 对该 tail 范围的至少三个额外尺寸固定核提升 `>= 3%`；
- Case 2 38 核中位数提升 `>= 5%`；
- Case 1/3/4 无超过 `1%` 的稳定回退；
- 代码尺寸增长不超过 SME worker 当前 text size 的约 35%，否则拆成冷路径函数。

### P3 预期贡献

目标总分 `+2%～+6%`，其中主要收益应出现在 Case 2。若只改善公开 kernelWidth、额外宽度失败，则按过拟合候选删除。

## 10. 阶段 P4：38 核显式任务区间与稳定性

### P4-1 基于工作量而非块数分区

当前任务权重受以下因素影响：

```text
rowCount
full 64-column block 或输出尾块
kernelHeight + rowCount - 1
kernelWidth 完整组和尾部
```

为每个二维任务计算通用估算权重，把累计权重区间连续分给 38 个线程。优先保持每线程列块连续，避免 `static,1` 已证明的缓存局部性退化。

### P4-2 两级策略

- 中核：连续静态区间，保证 packed/input 顺序访问；
- 大核：只在 P1 证明长尾时保留或调整 `guided,1`；
- 尾任务：把每个 row tile 的输出尾块分散到预计较轻的线程，但不使用运行时抢占；
- 小问题：保留现有低开销粗任务路径。

### P4-3 线程与 CPU 绑定

扫描并固定：

- `OMP_PROC_BIND=close` 与 `spread`；
- `OMP_PLACES=cores`；
- 38 核是否都在所选 NUMA 节点；
- 线程首次访问 packed kernel 和 output 的位置；
- `OMP_WAIT_POLICY=ACTIVE` 的稳定性。

不得跨 NUMA，也不得用超过 38 核换取成绩。

### P4 验收标准

- 最慢线程相对中位线程的结束时间差至少降低 30%；
- 38 核中位数提升 `>= 2%`，或相同中位数下运行变异系数降低 `>= 30%`；
- 固定核微内核性能不变化，证明收益来自并行调度；
- 额外尺寸无负载集中到单线程的反例。

### P4 预期贡献

性能 `+1%～+5%`，并降低官方成绩不稳定性。若 P1 显示线程长尾低于 3%，则该阶段只做稳定性收尾，不宣称大幅提升。

## 11. 阶段 P5：packed-kernel 与缓存供给联合优化

此前已经失败的方案不得原样重做：

- 不再增加 packed-row padding；
- 不复制整幅 input；
- 不用 ZA 部分和反复写回换 L1 复用；
- 不继续盲扫 physical-row 软件预取距离；
- 不压缩为破坏 64 B 连续 kernel load 的布局。

### P5-1 kernel 双缓冲和指针布局

在 P2 汇编内完成，不新增内存流量：

- 两个 kernel 向量寄存器轮换；
- packed kernel 保持每向量 64 B 对齐；
- 使用递增基址或合法的 `MUL VL` 地址形式；
- 让下一 physical row 的首个 kernel load 在当前行末尾发出；
- 对比是否真正减少 load-use stall，而不是只减少整数指令。

### P5-2 输入和 kernel 缓存事件分离

用两个诊断二进制分别固定 packed kernel 为 L1 热、input 为真实流，以及反过来，判断 L1D refill 的主要来源。只有确认来源后才允许加入针对性预取。

### P5-3 只接受无额外大流量的方案

任何候选先填写流量预算：

| 项目 | 当前字节数/输出块 | 候选字节数/输出块 |
|---|---:|---:|
| packed-kernel load | 待 P1 统计 | 必须不增加 |
| input load | 待 P1 统计 | 原则上不增加超过 5% |
| ZA/output store | 最终写回一次 | 不得增加部分和流量 |
| 临时缓冲 | 0 | 不得按输出规模增长 |

### P5 预期贡献

目标 `+1%～+4%`。该阶段主要用于帮助 P2 达到稳定收益，不能单独承担 80% 目标。

### P7-1 候选模型

- 不生成完整 im2col 的小块 implicit-Toeplitz；

### 20.1 本次修订的证据边界

- 每个 CPU core 有私有的 `32 KiB L1D` 和 `768 KiB L2`；
- 一个计算 NUMA 包含 38 个 CPU core；
- SVE/SME 向量宽度上限为 512 bit；
- FP32 矩阵算力口径为每周期 256 FLOP；
- 服务器 CPU 最高频率为 2.0 GHz，因此 38 核纯矩阵物理峰值约为 `19.456 TFLOPS`；
- 服务器处于片上内存 Flat 模式，CPU/DDR 节点为 0～15，4 GiB 片上内存节点为 16～31；
- 手册给出的单 NUMA 片上内存 STREAM 带宽约为 380～410 GB/s；
- 当前服务器透明大页为 `always`、CPU governor 为 `performance`，无需在参赛代码中重复修改；
- 当前服务器的 SVE 默认向量长度为 64 字节，但 SME 默认向量长度只报告 32 字节，与固定 16 个 FP32 lane 的内核假设不一致。

### 20.2 当前固定 16×64 SME 映射的结构上限

当前内核固定累计 16 个相邻输出行。为了覆盖这 16 行对应的卷积窗口，每个 row tile 必须遍历：

```text
kernelHeight + 15
```

个物理输入行。对某一输出行无效的边缘权重虽然被打包为零，但 `FMOPA` 指令仍会发射。因此该映射的理想有效比例为：

```text
kernelHeight / (kernelHeight + 15)
```

在 19.456 TFLOPS 物理峰值下，四个公开 Case 的映射上限为：

| Case | 当前映射理想上限 | 单项 18000 占比 | 当前官方成绩占该映射上限 |
|---|---:|---:|---:|
| Case 1，KH=39 | 14051.6 | 78.06% | 84.53% |
| Case 2，KH=41 | 14244.6 | 79.14% | 73.78% |
| Case 3，KH=55 | 15286.9 | 84.93% | 89.35% |
| Case 4，KH=81 | 16416.0 | 91.20% | 82.98% |
| 总计 | **59999.0** | **83.33% / 72000** | — |

该上限忽略了所有 load、store、EXT、分支、缓存未命中和 OpenMP 开销，仍低于 64800 GFLOPS 的 90% 总目标。因此 P2～P6 的低层优化只能逼近约 80%～83%，不能单独承担 90% 目标。下一阶段必须增加一种减少 row-tile 重叠工作的算法映射。

### 20.3 缓存事实修正

当前 packed kernel 的规模约为：

| Case | packed kernel | 单物理行 packed 数据 | 32 KiB L1 可容纳物理行数 |
|---|---:|---:|---:|
| Case 1 | 131.62 KiB | 2.44 KiB | 13 |
| Case 2 | 143.50 KiB | 2.56 KiB | 12 |
| Case 3 | 240.62 KiB | 3.44 KiB | 9 |
| Case 4 | 486.00 KiB | 5.06 KiB | 6 |

四项 packed kernel 都能放入每核 768 KiB L2，但都不能完整放入 32 KiB L1。因此后续缓存优化目标应是让当前 physical-row 或 phase 工作集停留在 L1，并让完整 packed kernel 稳定命中私有 L2；不能再假设整个 packed kernel 会留在 L1。

## 21. 新主线 R0：SME 向量长度安全化

### R0-1 风险

当前代码固定使用：

```text
tileSize = 16 FP32 = 64 bytes
```

但服务器当前的 SME 默认向量长度为 32 字节。如果线程以该长度进入 streaming mode，固定 16-lane 的打包、谓词、ZA 行号和写回都会失去成立条件。这类问题通常表现为校验失败或越界，而不是普通的 GFLOPS 波动。

### R0-2 实现方案

优先采用不修改测试器的进程初始化方案：

1. 在 `conv2d.c` 内通过构造函数或等价的进程早期初始化调用 `prctl(PR_SME_SET_VL, 64 | PR_SME_VL_INHERIT)`；
2. 确保该调用发生在 `bench_conv.c` 创建 OpenMP worker 之前，使后续线程继承 64 字节 SME VL；
3. 读取 `PR_SME_GET_VL` 复核实际长度；
4. 若系统不支持或设置失败，禁止进入固定 16-lane SME 路径并回退到 SVE/C；
5. 不执行 `sudo`，不修改 `/proc/sys/abi/sme_default_vector_length`，不改变系统全局状态。

### R0-3 验收

- 默认 SME VL 为 32 和 64 的环境中都不能出现错误的固定宽度 SME 执行；
- 64 字节环境下不引入每次 `conv2d` 调用的系统调用；
- 官方和额外正确性矩阵全部 PASS；
- 若官方不允许构造函数或 `prctl`，删除该候选并要求评测环境保证 SVL=64。

## 22. 新主线 R1：滚动 ZA 输出行环

### 22.1 算法目标

当前固定 row tile 会在每个 16 行块重复计算上下边缘。滚动 ZA 输出行环改为按物理输入行顺序扫描，并让 ZA 的每一行长期保存一个尚未完成的输出行：

```text
新输出行开始：清空分配给它的 ZA row
处理一个 physical input row：按 ik 递增更新全部活跃输出行
输出行完成最后一个 jk：写回对应 ZA row
ZA row 在安全间隔后循环复用
```

对每个输出元素，physical row 从 `outputRow` 增加到 `outputRow + kernelHeight - 1`，内层 `ik` 仍严格递增，因此累计顺序保持为参考实现的 `jk -> ik`。

### 22.2 ZA 容量和通用分派

同时活跃的输出行数量为 `kernelHeight`，需要的 ZA tile 数量为：

```text
groups = ceil(kernelHeight / 16)
```

FP32 SME 提供 ZA0～ZA3，因此第一版只在以下通用条件启用：

```text
1 <= kernelHeight <= 64
outputWidth 足以形成至少一个 16 列块
SME streaming vector length == 64 bytes
```

`kernelHeight > 64`、小输出宽度、列尾部和非 SME 机器继续走现有路径。该分派不判断任何公开 Case 的完整 shape。

### 22.3 数据映射

令：

```text
capacity = groups * 16
slot     = outputRow % capacity
tile     = slot / 16
lane     = slot % 16
```

因为 `capacity >= kernelHeight`，一个 lane 再次分配给新输出行前，旧输出行一定已经完成并写回。每个 physical row 只增加一个新输出行、完成一个旧输出行，热循环只增加一次 ZA row 清空和一次 16-lane 写回。

卷积核打包按通用 phase 生成：

```text
[physicalRow modulo capacity][tile][kernelColumn][16 lanes]
```

每个 lane 存放当前 physical row 对应输出行的 `kernel[jk][ik]`，不活跃 lane 为零或由谓词关闭。第一版优先保证正确；若 phase pack 过大或 L2 refill 明显增加，再改为 16-phase 循环布局或双缓冲加载。

### 22.4 并行方式

滚动环占用 3～4 个 ZA，因此一次只计算 16 个输出列。OpenMP 任务按连续的 16 列块划分：

- 每个任务独立清零 ZA，并完整扫描 inputHeight；
- 输出列块数量约 250～400，足以覆盖 38 核；
- 每个线程尽量取得连续列区间，避免 `static,1` 破坏输入局部性；
- 列尾继续走现有泛化路径，第一版不在同一任务中混合不同列宽。

### 22.5 理论上限与诚实预期

滚动环的主要 padding 变为：

```text
kernelHeight / (16 * ceil(kernelHeight / 16))
```

| Case | groups | 理想有效上限 | 占单项 18000 |
|---|---:|---:|---:|
| Case 1 | 3 | 15808.0 | 87.82% |
| Case 2 | 3 | 16618.7 | 92.33% |
| Case 3 | 4 | 16720.0 | 92.89% |
| Case 4 | 6 | ZA 不足，保留当前路径 | 91.20% 当前映射上限 |

这些是忽略访存和调度的物理上限，不是预测成绩。滚动方案会减少 `FMOPA`，但增加 packed-kernel vector load 密度，并把输出列宽从 64 降到 16。可信的第一阶段目标是 Case 1～3 固定核提升 5%～15%、38 核总分提升 3%～8%，而不是直接承诺 90%。

## 23. R1 的实施拆分与停止条件

### R1-A：标量状态机验证

- 在独立诊断代码中验证 slot/tile/lane 生命周期；
- 对 `KH=1,15,16,17,31,32,33,39,41,55,63,64` 检查无碰撞；
- 输出每个 lane 的 start、update、retire、reuse 时刻；
- 不进入正式性能代码。

### R1-B：单线程 ACLE 正确性原型

- 使用 `svwrite_hor_za32` 或编译器支持的等价方式清空单个 ZA row；
- 使用 `svst1_hor_za32` 写回完成行；
- 先使用简单 phase pack，不做软件流水；
- 列尾和不支持的 KH 回退现有实现。

### R1-C：固定核周期筛选

分别记录：

- `FMOPA` 静态/动态数量；
- kernel/input vector load；
- 每个 physical row cycles；
- L1D/L2D access/refill；
- ZA row store/clear 开销；
- Case 1/2/3 固定核中位数。

进入 38 核的最低门槛：Case 1～3 至少两个提升 `>=5%`，另一个不回退超过 2%。

### R1-D：38 核并行版本

- 使用连续 16 列任务；
- 比较 static 连续区间、runtime static 和小粒度 guided；
- 记录逐线程完成时间，确认没有整幅 input 扫描造成新的长尾；
- 四个官方 Case 与非公开尺寸全部 PASS。

保留门槛：同期四 Case 总分提升 `>=3%`，且任何 Case 不稳定回退不超过 1.5%。

### R1-E：加载流水与汇编

只有 R1-D 通过后才进行：

- 下一 tile kernel vector 双缓冲；
- 跨 16 个 `ik` 的输入窗口携带；
- phase pack L1 工作集压缩；
- 完整 physical-row 热循环汇编；
- 最后一组部分活跃 ZA 与 SVE 混合的成本比较。

每个候选仍执行独立 A/B；不得把多个低置信度改动一次叠加。

## 24. 新主线 R2：片上内存合规性门控实验

测试程序验证阶段峰值内存约 380～408 MiB，正式计时阶段约 300 MiB，小于单片上节点 4 GiB。服务器 Flat 模式下，CPU node `n` 对应的片上内存节点通常为 `n + 16`。

但 `numactl -N 7 -m 23` 在 Linux 中涉及两个 NUMA node ID，与赛事“单一 NUMA”限制存在解释歧义。因此该方向分为严格门控的三个步骤：

1. 向官方书面确认“一个 CPU NUMA + 其对应片上内存节点”是否属于允许的单 NUMA资源；
2. 未确认前只记录拓扑，不执行或提交该绑定；
3. 确认允许后才做 DDR 与片上内存的交错 A/B，并记录实际 node page 分布和带宽。

片上内存不是滚动 ZA 的正确性前提。若官方不允许，R1 必须在普通本地 DDR 上仍然成立。

### 26.4 失败原因：减少 FMOPA，却破坏了 kernel-vector 复用

固定 16×64 内核每次加载一个 16-lane packed-kernel vector，可复用于 ZA0～ZA3 的四个 16 列输出块：

```text
约 1 个 kernel vector + 少量滑窗 input load -> 4 个 FMOPA
```

滚动 ZA 为保存 39～64 个同时活跃的输出行，占用 3～4 个 ZA，只剩一个 16 列输出块。每个 `ik` 必须为不同 ZA 分别加载不同的 kernel vector：

```text
3～4 个 kernel vector + 1 个 input vector -> 3～4 个 FMOPA
```

虽然 Case 1 理论上减少约 10.3% 的 `FMOPA`，但 kernel-vector load/MOPA 从约 `0.25` 上升到约 `1.0`，接近四倍；phase pack 只能驻留 L2，无法让全部向量长期停留在 32 KiB L1。实测约三倍变慢与这一供给模型一致。

这给出了一个新的必要条件：任何替代映射在编码前不仅要减少 `FMOPA`，还必须保持“一个 kernel vector 至少复用多个输出列 ZA”的性质。只减少 row halo、却把 ZA 全部用于输出行分组的方案不可行。

### 26.5 R1 决策

- 滚动 ZA 第一版从默认性能路径撤回；
- 不继续为其扫描 phase 数、预取、OpenMP chunk 或汇编顺序，因为这些优化无法弥补约 3× 的供给差距；
- 状态机正确性结论和失败成本模型保留在文档中；
- 正式源码不得长期保留默认关闭的失败内核；完成本轮审计后删除原型实现；
- 后续新映射必须同时填写 `FMOPA`、kernel load、input load、ZA 占用和部分和流量预算。

### 27.3 滑动尾部实验：正确但性能失败

当前 39、41、55 宽 kernel 在完整 16 列组后分别剩余 7、9、7 列。理论上可把尾部每列四次输入向量加载改成五向量滑动窗口，例如 7 列从 28 次输入加载降到约 5 次。先后实现了：

1. 运行时长度的滑动尾循环；
2. 按 `kernelWidth % 16` 的 1～15 通用余数分类和 fall-through 编译期展开。

两种版本在多种余数宽度上都保持最大误差 0，但 Case 2 从控制版约 `10662～11129` 降至 `8339～8790 GFLOPS`，退化接近 20%。原因不是数学错误，而是额外五个长生命周期 SVE 窗口增加了 SME streaming 函数的寄存器压力和搬运。该原型已完整删除，不留默认关闭的死代码。

### 27.5 成功改动一：中等 kernel 的 L2 输入预取

当前计算按 physical row 跳跃访问输入，不同输入行之间相隔一个完整 `inputWidth`，硬件顺序预取器难以同时跟踪大量短行流。本轮在不改变任何计算和累加顺序的前提下，为未来第 4 个 physical row 预取输入区间的若干代表缓存线：

```text
当前 physical row r 计算
    ↓
预取 physical row r + 4 的 input + {0, 32, 64, 96} 个 float
    ↓
数据先进入 L2，四轮计算后再被真正读取
```

该路径只用于通用的 41～64 kernel-width 类别；宽 kernel 的预取会与更多并行列任务争夺缓存，因此不启用。最终交错 A/B 中，Case 2 从平均 `10938.84` 提升到 `11471.95 GFLOPS`，约 `+4.87%`；Case 3 接近中性，未出现确定退化。Case 1 不执行预取主体。

| 6 | 12439.4705 | `-3.0%` |

五分区恰好把该轮 65 个完整列块分成等长工作，同时仍让每个任务连续处理多个列块，兼顾线程尾差和输入/cache 局部性。实现按 `kernelWidth > 64` 这一通用类别选择五分区，不判断完整公开 Case 尺寸；额外 `67×73`、`83×79` kernel 尺寸均 PASS。

## 28. 2026-08-31 13:51–14:25 CST｜SME 指令调度与宽核输出预取迭代

### 28.1 本轮问题与测量方法

上一轮保留了中等 kernel 输入预取和宽 kernel 五分区，但固定 `16×64` SME 内核本身仍只达到单 Case 理论上限的约 64%～75%。本轮不先假设瓶颈，而是依次完成：

2. 使用 `perf record/annotate` 定位热指令；
3. 分离“机器指令调度”“输入预取”“输出预取”“任务数”四类候选；
4. 每类先检查目标文件是否真的变化，再做额外尺寸正确性；
5. 对可能保留的候选做正反序交替 A/B，不用单次峰值决策。

服务器是共享环境。全机 load average 一度超过 80，但 `/proc/stat` 的逐 CPU 两秒差分显示节点 7 在采样时可达到约 99.9% idle；因此全机 load 不能直接判断绑定节点是否繁忙。即便如此，其他任务仍可能在测试过程中进入节点，Case 4 曾出现控制版和候选版同时跌到约 `3～4 TFLOPS` 的污染轮次，该轮已明确作废。

### 28.2 热循环证据

反汇编确认完整 16 列 kernel 组的主要序列为：

```text
加载 1 个 packed-kernel SVE vector
连续 5 次 EXT，生成四个 16 列输入窗口并更新 carry window
连续 4 次 FMOPA，累加到 ZA0～ZA3
```

`perf annotate` 的样本主要落在 `FMOPA`、输入/packed-kernel 的 `LD1W` 和反复出现的 `EXT` 上。该采样包含 OpenMP 运行时和参考实现，不能把某条指令的样本百分比直接解释成周期占比，但足以确认优化对象是 SME 热循环而不是标量尾部。

这个证据同时说明两件事：

- 现有内核已把一个 kernel vector 复用到四个 ZA，算术映射是合理的；
- `EXT` 与 `FMOPA` 的排列可能存在流水机会，但必须通过生成代码和实测证明，不能只看 C/ACLE 源码顺序。

### 28.3 双窗口与源码交错：生成代码反证

先后尝试两个不改变数学顺序的源码级调度：

1. 两套 SVE window 变量交替滑动；
2. 在源码中写成 `EXT → FMOPA → EXT → FMOPA`。

双窗口控制版与候选版对象大小同为 `11619` 字节，反汇编差异只有约 10 行，实质是两个地址寄存器交换；源码交错也只移动了一条地址更新。BiSheng 后端将两种源码重新调度回原来的指令组，因此它们不具备可测性能差异。两个试验均已删除，没有把无效果的复杂度留在正式实现中。

### 28.5 零指令依赖约束：机器码成功、性能失败

```text
模式 1：EXT, FMOPA, EXT, FMOPA, EXT, FMOPA, EXT, FMOPA
模式 2：EXT, EXT, FMOPA, FMOPA, EXT, EXT, FMOPA, FMOPA
```

这一次目标文件真正改变：text 从 `11619` 降到 `11491` 字节，反汇编约 3972 行不同，热点确实形成一条一条或两条一组的交错序列，且栈 load/store 计数没有增加。额外 `17×19`、`43×37`、`67×73`、`83×79` kernel 均为最大误差 0、PASS。

本轮结果把可行空间进一步缩小：

1. 普通编译器调度参数、源码交错和零指令强制交错均已实测，不能作为大幅提升来源；
2. 输入预取在小核/宽核无收益，输出预取只剩宽核 1 行这一处稳定增益；
3. 任务数在当前五分区附近已呈明显噪声，继续搜索只能获得偶然峰值；
4. 达到 80%～90% 仍需要改变每单位数据搬运对应的有效 FMOPA 数，或减少物理行 halo 的重复工作，同时保留“一个 kernel vector 复用四个 ZA”的优势；
5. 若写手工汇编，重点不应只是重新排列现有 5 EXT/4 FMOPA，而应尝试跨两个 kernel shift 的 kernel load 提前、软件流水和明确的双迭代资源模型，并先用独立微基准确认鲲鹏 920 SME 的 FMOPA/EXT 吞吐和延迟；
6. 新算法在编码前必须同时列出 FMOPA 数、kernel/input load 数、ZA 占用、L1/L2 工作集和浮点累加顺序。无法在纸面模型上超过当前 16×64 映射的方案不再实现。

本轮获得的是一个可保留的缓存优化和多组有价值的失败反证，不应把约 5.19% 的 Case 4 增益描述成已经接近 90%。当前整体仍约在理论总上限 69% 左右，下一阶段必须转向可测微架构模型或新的高复用映射。

## 29. 2026-08-31 11:20–15:20 CST｜以单项 +2000 GFLOPS 为目标的结构实验

### 29.1 目标换算与验收口径

参赛者提出“每个 Case 至少再提高约 2000 GFLOPS”。若以官方榜单 `49667.4161 GFLOPS` 为起点，这对应约 `57667.4161 GFLOPS`，即四项理论总上限的约 `80.09%`。这个目标是合理的 80% 阶段线，但它要求四项合计增加约 `8 TFLOPS`，不可能靠一个预取常数或一处循环展开完成。

本轮继续遵守以下边界：不修改测试程序、不复用或漏算输出、不判断公开输入的完整 shape、单 NUMA、最多 38 核、最大误差不超过 `1e-5`。所有结构候选先验证额外尺寸，再进入官方尺寸 A/B；退化候选从正式源码完整删除。

### 29.2 kernel 尾部补齐：计算量模型正确但方向失败

第一个假设是把 kernel width 补齐到 16 的倍数，用零 kernel 系数把直接加载尾部转换成完整 SME 滑窗组。它安全且误差为 0，但会执行零系数对应的额外 `FMOPA`：

| Case | 控制版 GFLOPS | 补齐候选 GFLOPS | 变化 |
|---|---:|---:|---:|
| Case 1 | 11653.6248 | 9523.2543 | `-18.3%` |
| Case 2 | 11424.7627 | 9736.3878 | `-14.8%` |
| Case 3 | 13384.9365 | 11446.3578 | `-14.5%` |

结论是：评测 GFLOPS 的分子只计算真实卷积操作，零系数外积不会增加得分，只会延长时间。该候选已删除。

### 29.3 成功候选：复用主循环五窗口处理尾部

此前失败的 fresh-tail 原型为尾部新建五个长生命周期窗口，造成寄存器压力。本轮改为复用完整组结束时已经存活的 `window0..window4`：每个 tail kernel 列执行四次 `EXT`，随后只用一个 lane 的谓词加载补入下一元素。它具有三个重要性质：

1. 不增加 `FMOPA` 数；
2. kernel 列仍按原顺序累加，额外尺寸最大误差为 0；
3. 不增加另一套五窗口寄存器，避免重演此前约 20% 的回退。

发现交互 shell 未绑定 NUMA 后，重新使用 `OMP_NUM_THREADS=38 numactl -N 7` 做 `test_runs=9`、三轮正反序 A/B，结果为：

| Case | 控制均值 GFLOPS | 候选均值 GFLOPS | 稳定变化 |
|---|---:|---:|---:|
| Case 1 | 11761.9684 | 12249.0571 | `+487.0887，+4.14%` |
| Case 2 | 11481.6592 | 11544.9872 | `+63.3280，+0.55%` |

该优化按通用 `kernelWidth <= 64` 类别门控；大于 64 的宽核继续使用原直接尾部。Case 3 的测试主要在中性到小幅正向之间，未把单次峰值当成稳定收益。

两个放大尝试均失败：把所有待补 lane 一次加载成 feed vector，Case 1 从约 `12123.7` 跌到 `8607.9 GFLOPS`；将 carry-tail 展开 2/4 路，Case 1 从约 `12004.5` 分别降至 `11945.0/11875.3 GFLOPS`。说明这一尾部路径已接近当前寄存器和依赖平衡，继续展开不能获得千级收益。

### 29.4 2×2 ZA 映射：减少 EXT，却触发加载瓶颈

当前四个 ZA tile 采用 `16 行 × 64 列` 横向映射。本轮实现了泛化的 `32 行 × 32 列` 2×2 映射，希望把每个 kernel 列的四条滑窗依赖改成两个输入向量和两个 kernel 向量。多组奇偶尺寸及 kernel width 31/32/39/41/55/81 均误差 0，但官方性能为：

| Case | 16×64 控制 | 32×32 候选 | 结论 |
|---|---:|---:|---|
| Case 1 | 11514.4623 | 9839.6292 | `-14.5%` |
| Case 2 | 11497.4089 | 8302.9348 | `-27.8%` |
| Case 3 | 13386.8688 | 6929.9940 | `-48.2%` |
| Case 4 | 13526.1293 | 4200.8233 | `-68.9%` |

大 kernel 的退化随 width 增大而放大，证明该机器上重复 L1 非对齐向量加载和第二条 packed-kernel 流远比 `EXT` 昂贵。2×2 代码已删除；当前一个 kernel vector 复用四个横向 ZA 的映射仍更合理。

### 29.5 指令调度屏障与完整 16 列汇编流水

反汇编显示毕昇把热步排成连续 5 条 `EXT` 后接 4 条 `FMOPA`。本轮做了两层更严格的验证：

- 用零机器指令的 SVE 寄存器约束强制形成 `EXT/FMPA` 交错，生成代码确实改变，但四项约为 `-1.5%～+0.3%`，总体无收益；
- 编写完整 16 列 SME inline-asm，固定 `z0..z6/p0..p2`，用 `MUL VL` 寻址，并在多个完整组之间携带五个输入窗口。全部额外尺寸误差为 0；相邻官方 A/B 只有约 `-0.4%～+0.7%`。

这推翻了“删除整数偏移 MOV 就能带来大幅提升”的假设。当前编译器生成的稳态循环已经接近这一层手工排程；真正的汇编突破必须跨两个或更多 kernel shift 建立 kernel 双缓冲，并用微架构吞吐/延迟模型安排两套在途操作，而不是把同一批九条核心指令换序。

### 29.7 为什么本轮仍没有达到每项 +2000，以及下一项大改造

本轮没有达到“每项 +2000”，不能把约 `+0.1～0.45 TFLOPS` 的可归因收益包装成 `+2 TFLOPS`。实验已经证明以下方向不足以提供两位数收益：零填充、普通展开、换 ZA 形状、增加向量加载、单迭代指令换序、删除地址生成 MOV。

下一项具备大幅提升可能性的工作应是**真正的跨迭代双缓冲外部 `.S` 微内核**：

1. 先在固定单核探针上分别测 `FMOPA`、`EXT`、L1 `LD1W` 的吞吐与依赖延迟；
2. 设计两套 kernel 寄存器，提前至少一个 shift 加载下一 kernel vector；
3. 将窗口生成和当前/下一组的四条 `FMOPA` 交错，保证 ZA 更新端持续有独立指令；
4. 固定 packed-kernel 与 input 指针寄存器，避免 C 编译器跨 asm 边界重新搬运；
5. 单核先要求相对 ACLE 稳态探针提升至少 10%，再投入 38 核、缓存和任务调度验证；
6. 分别保留通用 remainder 0–15 尾部和非 SME 回退，不用完整公开 shape 分派。

只有该方案在单核微基准上先获得约 10%–15% 的真实吞吐提升，才有机会结合已有任务均衡、缓存和尾部收益向每项 `+2000 GFLOPS` 靠近。若单核仍无两位数收益，则当前直接卷积映射已接近其实现上限，需要重新评估保持 `1e-5` 精度的算法级变换，而不是继续扫参数。

## 30. 2026-08-31 15:25–16:20 CST：理论峰值复算、分带架构反证与片上内存发现

### 30.1 为什么这次停止继续扫小参数

本轮问题是“Case 1 的成功能否复制到其他 Case，以及能否从理论上限反推新的快速架构”。因此先把三个不同概念分开：

1. 赛事给出的单 Case 合规上限 `18000 GFLOPS`；
2. 当前服务器在实际频率下的 FP32 SME 原始硬件峰值；
3. 当前 `16×64` 直接卷积映射因为 row halo 而能取得的最高**评分 GFLOPS**。

鲲鹏 920 专业版手册给出：512-bit FP32 SME 每核每周期可完成 `256 FLOP`。服务器实测最高频率约 `2.0 GHz`，因此 38 核原始峰值为：

```text
38 × 2.0 GHz × 256 FLOP/cycle = 19456 GFLOPS
```

此前纯 ZA0～ZA3 `FMOPA` 探针约 `508.7 GFLOPS/核`，与 `2.0 × 256 = 512 GFLOPS/核` 基本吻合，说明该峰值模型不是纸面空算。

官方 `18000` 的精确内部公式尚未公布。一个高度吻合、但必须标为推测的来源是：手册建议每个 NUMA 留 1 个 housekeeping 核，并按约 `1.9 GHz` 计算，即：

```text
37 × 1.9 GHz × 256 = 17996.8 GFLOPS ≈ 18000 GFLOPS
```

也可能等价地使用 38 核、约 1.85 GHz 的保守频率。本文不把该推测当成官方事实，只用它解释 `18000` 与硬件规格为何接近。

### 30.2 当前 16×64 映射的自身上限

当前内核一次持有 16 个输出行。为了让这 16 行完成一个高度为 `KH` 的卷积核，需要扫描 `KH+15` 个物理输入行；评分分子只承认 `KH` 行真实卷积工作，而零 lane/无效 lane 占用同样的 `FMOPA` 发射时间。因此，在该映射达到 38 核 `19456 GFLOPS` 原始峰值的理想条件下，单 Case 的映射上限是：

```text
mapping_cap = 19456 × KH / (KH + 15)
```

| Case | KH | 当前映射上限 GFLOPS | 当前代表值 | 已达到映射上限 | 映射内剩余空间 |
|---|---:|---:|---:|---:|---:|
| 1 | 39 | 14051.56 | 12249.0571 | 87.17% | 1802.50 |
| 2 | 41 | 14244.57 | 11544.9872 | 81.05% | 2699.58 |
| 3 | 55 | 15286.86 | 13674.1997 | 89.45% | 1612.66 |
| 4 | 81 | 16416.00 | 13418.4321 | 81.74% | 2997.57 |

这张表给出两个关键结论：

- Case 1 和 Case 3 已经分别达到当前映射自身上限的约 87% 和 89%，继续只调预取、尾部展开或 task 数，很难各自再增加 `2000 GFLOPS`；Case 1 的映射内绝对空间甚至不足 `2000`。
- 即使把 Case 1 的 87.17% 映射效率完全复制到 Case 2/4，二者也只约为 `12417.3 / 14310.2 GFLOPS`，相对当前只增加约 `872 / 892 GFLOPS`。所以“复制 Case 1 技巧”是必要但不充分条件。

该上限只约束当前固定 `16×64` 映射，不是所有合法卷积算法的数学上限。榜首约 `17100 GFLOPS` 已超过该映射的四项上限，说明其要么使用了不同计算映射/系统策略，要么最终还需要接受官方人工合规检查；在没有代码证据前不能反推或模仿其实现。

### 30.3 新架构：kernel-height 分带 + 四 ZA 横向复用

此前滚动 ZA 把 3～4 个 ZA 用作输出行环，只剩 16 个输出列，导致一个 kernel vector 的复用从 4 次降为 1 次，Case 1 约三倍变慢。本轮设计了不同版本：

- ZA0～ZA3 仍全部表示相邻 64 个输出列，保持 `1 次 kernel load → 4 次 FMOPA`；
- kernelHeight 按最多 16 行分带；
- 每个分带内部把 16 个活跃输出行作为 ZA row 环；
- 分带结束时写回部分和，下一分带按原 `jk→ik` 顺序加载并继续；
- kernel phase 打包按通用 `ceil(KH/16)` 生成，不识别四个公开完整 shape；
- 64 列主块和谓词化列尾都使用 SME，额外 `7/16/17/19` 等高度边界与非 64 倍数宽度均为 `0.00e+00 PASS`。

纸面 `FMOPA` 物理行因子从 `KH+15` 变为 `16×ceil(KH/16)`：

| Case | 原因子 | 分带因子 | 理论 FMOPA 减少 |
|---|---:|---:|---:|
| 1 | 54 | 48 | 11.1% |
| 2 | 56 | 48 | 14.3% |
| 3 | 70 | 64 | 8.6% |
| 4 | 96 | 96 | 0% |

这满足“先证明算术量下降再编码”的条件，但实测否决了它：

| Case 1 版本 | 内存策略 | GFLOPS | 相对同策略当前内核 |
|---|---|---:|---:|
| 当前 16×64 | DDR | 12155.2614 | 基线 |
| 分带、跨全高长条 | DDR | 2463.2337 | -79.7% |
| 分带、256 输出行缓存块 | DDR | 7086.0965 | -41.7% |
| 当前 16×64 | 配对片上内存 | 12094.8083 | 基线 |
| 分带、256 输出行缓存块 | 配对片上内存 | 8403.8968 | -30.5% |

失败原因不是正确性，也不是 64 列 kernel 广播丢失，而是每个 height band 都必须把完整输出部分和从 ZA 写回并重新加载。256 行分块恢复了任务并行度和 L1/L2 局部性，片上内存又让候选提高约 18.6%，但都无法抵消 ZA partial spill/reload、纵向长 stride 和多轮输出流量。该实现已经从正式 `conv/conv2d.c` 完整删除，不保留默认关闭的失败宏。

由此得到新的硬门槛：下一种大架构必须同时满足：

1. 一个 kernel vector 仍至少服务多个横向 ZA；
2. 输出只在最终完成时写回一次；
3. 每个输出保持原始 `jk→ik` FP32 累加顺序；
4. 纸面上同时降低 `FMOPA`、kernel/input load 或关键依赖，不用输出部分和交换算术量。

### 30.4 成功发现：配对片上内存对 Case 2/4 有明确收益

服务器 `numactl -H` 确认共有 32 个 NUMA ID：0～15 为带 CPU 的 DDR 节点，16～31 为各 4 GB、无 CPU 的片上内存节点。计算节点 7 的配对片上内存为节点 23。按手册方式使用：

```text
OMP_NUM_THREADS=38 numactl -N 7 -m 23 ./baseline ...
```

相邻单次 A/B 为：

| Case | DDR GFLOPS | 片上内存 GFLOPS | 变化 |
|---|---:|---:|---:|
| 1 | 12155.2614 | 12094.8083 | -60.4531，-0.50% |
| 2 | 11447.5610 | 11804.8376 | +357.2766，+3.12% |
| 3 | 13508.3900 | 13525.4276 | +17.0376，+0.13% |
| 4 | 13621.6806 | 14492.2964 | +870.6158，+6.39% |
| 合计 | 50732.8930 | 51917.3699 | **+1184.4769，+2.33%** |

这不是每项 `+2000`，但它是本轮唯一有明确正向幅度的新系统方向，也证明 Case 2/4 比 Case 1/3 更受访存供给约束。Case 1/3 没有收益，说明它们更接近 SME/窗口发射上限；不能把所有 Case 都简单归因于 DDR 带宽。

当前**没有**把 `-m 23` 写入 `conv/run.sh`。原因是赛事写明“单一 NUMA”，而 Flat 模式下计算节点 7 与其片上内存节点 23 会显示为两个 NUMA ID。系统手册明确推荐这种配对方式，但赛事是否把“一个计算 NUMA + 配对片上内存”视作合法单 NUMA 资源，仍需官方书面确认。确认前它只是一条实验结果，不是提交候选。

### 30.5 对 80%～90% 目标的修正路线

排行榜第 2～第 7 名从 Case 1 到 Case 4 大体递增，与 `KH/(KH+15)` 随 KH 增加而提高的趋势一致；这更像同类 `16×64` 或相近 direct-SME 映射把稳态效率做到约 91%～98%，而不是四套完全不同算法。短期合理目标是先逼近这组成绩：

1. 若官方允许，先用配对片上内存取得 Case 2/4 的可复现增益；必须采用统一、可解释的内存策略，不能按四个完整公开 shape 特判。
2. 对现有 `LD1W → 5 EXT → 4 FMOPA` 稳态块做真正跨两个 shift 的双 kernel 缓冲；此前汇编只是重排同一批指令，未建立两套在途 load。单核微基准不提升至少 10% 就停止。
3. 把“达到官方 90%”和“达到当前映射 90%”分开。Case 1/3 已接近后者；前者要求超过当前映射上限，必须出现不产生输出部分和的新 Toeplitz/SME 映射，现阶段尚未找到经实测成立的版本。
4. FFT、Winograd、普通 GEMM、低秩/可分离分解在随机稠密 kernel 和绝对误差 `1e-5` 下不能保留原 FP32 累加轨迹，已经有精度或性能反证，不再把它们写成可保证达到 90% 的路线。

诚实结论是：本轮找到了一个约 `+2.33%` 总分的待合规确认系统策略，并用完整二进制否决了一个纸面可减 8%～14% FMOPA 的大架构；尚未获得每项 `+2000`。要进入 80% 附近，最可信的代码路线不是继续扫宏，而是把当前映射的 Case 2/4 稳态效率从约 81% 推到 90% 以上；要进入官方 90%，仍需要尚未被证明的新数学映射，不能预先承诺。

### 30.6 2026-09-02：8 行 row-tile 架构原型否决

为验证“缩小 row tile、减少 `kernelHeight+rowTile-1` 物理行”是否能直接减少 FMOPA，单独复制提交目录构建了 `rowTile=8` 原型。原有 16×64 SME 汇编路径因 `rowCount != 16` 被禁用，四个公开尺寸均通过校验，但单次结果约为 `7264 / 7247 / 7937 / 8339 GFLOPS`，合计约 `30787 GFLOPS`，比当前 16×64 路径低四成以上。

这说明 SME 的谓词化 8 行并不会按比例减少 FMOPA 发射，反而失去 16 行微内核、增加任务数和尾部处理；仅改变 row tile 不能形成更高上限，原型未合入正式 `conv/conv2d.c`。

### 30.7 2026-09-02：16×128 多 ZA 原型的硬件接口限制

随后尝试保持 16 行、把横向块扩为 128 列，并用 8 个 ZA tile 保存结果。该版本在毕昇 SME 编译器阶段即被拒绝：FP32 的 `svmopa_za32_f32_m` 与 `svst1_hor_za32` intrinsic 的 tile 参数合法范围是 `[0, 3]`，不能直接访问第 4～7 号 tile。若要扩到 128 列，只能在 4 个 ZA tile 之间分批，并把部分和写回内存后再加载；这正是此前分带架构的主要损失来源，因此该方向不再作为直接内核方案。
