## 1. AI 核心判断

### 1.1 为什么原来的 SVE 路径很难继续提升

原始四重循环一次只累加一个输出元素。第一轮 SVE 优化把多个相邻输出列放进向量 lane，解决了标量依赖链和自动向量化问题，但本质上仍然是：

```text
一个 kernel 系数 × 一个输入向量 → 一个输出向量
```

显式 SVE 最终四项总分约为 `5833.8272 GFLOPS`。继续增加累加器、展开循环或改变普通预取，只能改善指令调度和缓存细节，无法改变每条 FMA 只沿一个维度工作的事实。

AI 当时的关键判断是：相邻输出行之间会复用同一物理输入行，这个结构不是普通的一维向量复用，而是一个二维外积：

```text
16 个输出行对应的 kernel 系数向量
        ×
16 个输出列对应的 input 数据向量
        ↓
16 × 16 个输出累加值确认 CartSee、BI 数据集市、风险日志、Shopify 同步及缓存刷新监听均已启动
```

这正好对应 SME `FMOPA`。因此，真正有数量级潜力的方向不是继续堆叠 SVE 累加器，而是把循环重写为 SME 外积。

### 1.2 最终结果说明了什么

| 指标 | 同机初版 | 显式 SVE | 当前 SME |
|---|---:|---:|---:|
| 四项总性能 | 254.3092 | 5833.8272 | **48612.1378 GFLOPS** |
| 相对初版 | 1× | 22.94× | **191.15×** |
| 相对显式 SVE | — | 1× | **8.33×** |
| 理论总上限占比 | 0.35% | 8.10% | **67.52%** |
| 正确性 | PASS | PASS | **PASS，最大误差 0** |

这些数据支持两个结论：

1. SME 外积映射是正确的主方向，贡献远大于普通循环展开或编译参数；
2. 当前 67.52% 之后的瓶颈已经从“没有使用合适的指令”转变为“SME 发射效率、额外行计算、加载供给和共享节点波动”。

### 1.3 目标不是停在 70%

`70%` 只是第一个阶段性目标，用来判断当前 SME 路线是否已经进入高利用率区间，不是项目终点。目标层级调整为：

| 阶段 | 单 Case 目标 | 四项总目标 | 意义 |
|---|---:|---:|---|
| 当前 | 约 59%–75% | 48612.1378 | SME 主路径成立，Case 3/4 已越过 70% |
| 第一阶段 | 70%，即 12600 | 50400 | 四项都进入较高利用率区间 |
| 第二阶段 | 80%，即 14400 | 57600 | 需要解决明显的结构和流水线浪费 |
| 第三阶段 | 90%，即 16200 | 64800 | 需要非常接近硬件与算法映射的最佳状态 |
| 长期目标 | 在合法范围内尽量接近 100%，但不超过 18000 | 尽量接近 72000 | 持续优化，而不是达到 70% 后停止 |

追求接近 100% 必须同时满足正确性、泛化、单 NUMA、38 核以及单 Case 不超过 `18000 GFLOPS`。如果结果异常超过上限，应先排查漏算、结果复用、计时和未定义行为，不能把异常高分当成成功。

## 3. 成功的尝试及原因分析

### 3.1 成功：四行纵向 SVE 复用

这是从 SVE 转向 SME 的关键中间实验。

原来每个输出行独立读取输入。改成同时计算 4 个相邻输出行后，同一个物理输入行可以为多个输出行服务。最初版本在热循环里判断每行是否有效，分支开销较大；消除稳态区间内的条件分支后，Case 1 从低效版本提升到约 `2752.6 GFLOPS`。

这个方案本身不是最终最快实现，但它提供了重要证据：

- 纵向复用确实存在；
- kernel 系数随输出行变化；
- input 数据随输出列变化；
- 两者组合天然形成外积。

### 3.2 成功：单 ZA 16×16 外积

单 ZA 实验的目标不是立刻取得最高分，而是验证以下问题：

1. `FMOPA` 的行、列方向是否与卷积映射一致；
2. ZA 横向写回是否能得到正确输出；
3. 流模式和 ZA 状态是否能在线程中安全使用；
4. BiSheng 的 ACLE 语法及链接依赖是否正确。

探针和完整 Case 均通过后，Case 1 达到约 `5242 GFLOPS`。它证明 SME 方案不是理论推测，而是可用的正确实现。

### 3.3 成功：从一个 ZA 扩展到四个 ZA

一个 ZA tile 只能覆盖 16×16 输出。服务器的 FP32 ZA 状态可以同时使用 4 个 tile，因此改为：

```text
ZA0 → 输出列  0–15
ZA1 → 输出列 16–31
ZA2 → 输出列 32–47
ZA3 → 输出列 48–63
```

同一个 kernel 系数向量被四个 tile 复用，只需替换输入列向量。Case 1 从约 `5242` 提升到约 `9275 GFLOPS`。

AI 对这一步的分析是：提升并非简单的 4 倍，因为计算、加载、ZA 清零和写回仍共享前端与缓存资源；但 4 tile 显著提高了每次 kernel 向量加载能够完成的有效工作量。

### 3.4 成功：卷积核打包

对于固定物理输入行和 kernel 列，16 个输出行需要的系数来自不同 kernel 行，原始内存中不是连续向量。最终使用：

```text
packedKernel[physicalRow][kernelColumn][outputRowLane]
```

打包后一次连续 SVE 加载即可得到 `FMOPA` 左操作数。无效 lane 写 0。缓冲区每次调用重新生成并释放，不缓存上一次卷积结果。

成功原因：它把热循环中的跨行索引、条件选择和离散加载移到了计时内但占比较小的预处理阶段，换取大量连续加载。

### 3.5 成功：SME 内部的 SVE 滑窗

独立 SVE 滑窗曾严重退化，但放到 SME 16×64 微内核中后产生了小幅正收益。每 16 个 kernel 列：

- 加载 4 个完整输入向量和第 5 个扩展向量；
- 使用 `svext_f32` 构造偏移 1–15 的窗口；
- 每个窗口分别更新 4 个 ZA tile。

这里能够成功，是因为 `EXT` 构造出的每个输入向量会驱动高密度的 SME 外积，而不是只驱动普通 SVE FMA。Case 1 由约 `9275` 提升到约 `9406 GFLOPS`。

### 3.6 成功：输出写预取

ZA 累加结束时会连续写回 16×64 个 float。计算速度提高后，首次写入的缓存行分配会暴露在关键路径上。把输出行预取分散到最后几个物理输入行中，Case 1 曾从约 `9406` 提升到约 `9954 GFLOPS`。

最终不是固定一个预取方式，而是使用宽度区间：

- kernel 宽 41–64：每个预取步处理两行；
- 其他宽度：每步处理一行。

这是一条基于工作量的通用启发式，不检查完整公开输入参数。

### 3.7 成功：测试程序和内核分开编译

`-ffast-math` 对内核有帮助，但如果同时作用于 `bench_conv.c`，参考实现会改变累加和融合行为，实测误差超过 `1e-5`。

最终方案：

```text
bench_conv.c：-O3，严格浮点语义
conv2d.c：    -O3 -ffast-math，允许内核调度优化
```

这是性能与正确性同时成立的必要工程修复。

### 3.8 成功：逐 lane 滚动窗口降低寄存器搬运

第一版 SME 滑窗对每个偏移分别写成 `svext(input0, input1, shift)`。数学上只需 60 个窗口拼接，但编译器为了保留所有原始输入并满足立即数 `EXT` 形式，在热块中生成了大量向量寄存器复制。改进版维护 5 个可变窗口，每次统一向前滚动 1 个 lane：

```text
window0 = EXT(window0, window1, 1)
window1 = EXT(window1, window2, 1)
window2 = EXT(window2, window3, 1)
window3 = EXT(window3, window4, 1)
window4 = EXT(window4, zero,    1)
```

汇编静态计数由“60 条 `EXT` + 77 条向量 `MOV`”变为“74 条 `EXT` + 22 条向量 `MOV`”。虽然 `EXT` 数略增，但净减少 41 条向量指令，并让每个窗口形成清晰的短生命周期。一次严格交错的 `test_runs=3` A/B 为：

| Case | 立即数窗口 | 滚动窗口 | 相对变化 |
|---|---:|---:|---:|
| Case 1 | 10325.5011 | 12088.9501 | +17.08% |
| Case 2 | 9784.4659 | 10920.0071 | +11.61% |
| Case 3 | 11075.0270 | 13521.9986 | +22.09% |
| Case 4 | 10004.5972 | 11774.6918 | +17.69% |
| 总计 | 41189.5912 | 48305.6476 | **+17.28%** |

这组结果说明优化关键不是盲目减少某一种指令，而是减少热循环总指令、寄存器保存压力和编译器生成的搬运。

### 3.9 成功：跨 16 列核组携带输入窗口

一个 16 列组结束时，滚动窗口已经位于下一组开始位置的前一 lane。再做一次边界 `EXT`，前 4 个窗口即可直接成为下一组输入；只需加载新的第 5 个向量。为避免越界，只有确实存在后续完整组时才完整加载第 5 个向量，最后一组仍使用 15-lane 谓词加载。

实测 39–55 宽的卷积核基本处于约 ±1% 波动区间，81×81 大核多轮提升约 7%–15%。这符合缓存判断：组数越多，可省掉的重复输入加载越多。实现按是否存在后续完整组决定复用，不检查四个公开输入尺寸，因此保持泛化。

### 3.10 成功：packed kernel 64 字节对齐

每个 packed-kernel 项是 16 个 `float`，正好 64 字节；缓冲区总大小也必然是 64 字节整数倍。普通 `malloc` 只保证基础类型所需对齐，首个 kernel 向量可能跨越两个缓存行。改用 `aligned_alloc(64, packedBytes)` 后，每个连续 kernel 向量都从 64 字节边界开始。

NUMA 5、两轮 `test_runs=5` 的交错 A/B 为：

| 轮次 | 普通 `malloc` 总分 | 64 字节对齐总分 | 相对提升 |
|---|---:|---:|---:|
| Round 1 | 47770.2635 | 48771.2519 | +2.10% |
| Round 2 | 46945.1125 | 48453.0236 | +3.21% |
| 两轮均值 | 47357.6880 | 48612.1378 | **+2.65%** |

所有 Case 均 PASS、最大误差为 0。该改动只影响临时 kernel 缓冲区地址，不改变输入、输出、卷积语义或累加顺序。

## 4. 失败的尝试及原因分析

### 4.1 失败：只做 SVE 横向滑窗

**假设：** 相邻卷积窗口高度重叠，`EXT` 可以减少输入加载。

**结果：** 正确，但 Case 1 仅约 `388 GFLOPS`。

**原因分析：** `EXT` 并没有减少最终 FMA 数量，反而增加了寄存器搬运和依赖；在普通 SVE 路径中，每个构造窗口只服务少量向量 FMA，无法摊薄开销。

**得到的经验：** 数据复用必须和更高密度的计算映射结合。相同滑窗放入 SME 外积后才有小幅正收益。

### 4.2 失败：4× kernel 列展开

**假设：** 更深的展开可以隐藏加载和 FMA 延迟。

**结果：** BiSheng 基本持平，GCC 部分 Case 下降。

**原因分析：** 更多同时存活的向量增加寄存器压力和指令体积，前端收益不足以覆盖代价。

**决策：** SVE 回退保留较稳定的 2× 展开。

### 4.3 失败：对整个程序启用 `-ffast-math`

**假设：** 全程序 fast-math 可以让编译器生成更激进的代码。

**结果：** 参考输出被重排，最大误差约 `8.39e-5`，超过 `1e-5`。

**原因分析：** 测试程序本身也被改变，比较基准不再保持官方语义。

**决策：** fast-math 只用于允许修改的 `conv2d.c`。

### 4.4 失败：`-mcpu=tsv110`

**假设：** 指定旧鲲鹏核心名称可能得到更成熟的调度模型。

**结果：** 多个 Case 误差约 `1.10e-3` 到 `1.03e-2`，明显 FAIL。

**原因分析：** 该目标与当前 CPU、SME 能力和浮点代码生成不匹配。

**决策：** 使用服务器实际识别的 `-mcpu=native`，BiSheng 对应 `linxicore6100`。

### 4.5 失败：SME 精确行谓词

**假设：** 顶部和底部无效 lane 不参与计算可以减少浪费。

**结果：** 正确，但慢约 2%–5%。

**原因分析：** 谓词能屏蔽 lane，却没有减少 `FMOPA` 指令数量；额外的谓词构造和控制反而增加开销。

**得到的经验：** 必须减少外积指令或物理行迭代，而不是只屏蔽同一条外积中的 lane。

### 4.6 失败：输入跨行预取

**假设：** 提前预取下一物理输入行可以隐藏 L1/L2 延迟。

**结果：** 没有稳定提升，部分运行下降。

**原因分析：** 连续输入访问已经容易被硬件预取识别；软件预取额外占用前端和缓存带宽，还可能过早替换有用数据。

**决策：** 移除输入预取，只保留收益更稳定的输出写预取。

### 4.7 失败：ZA 非临时写回

**假设：** 输出只写一次，非临时写可以减少写分配和缓存污染。

**结果：** Case 间表现混合，约在 ±1% 内波动。

**原因分析：** 从 ZA 读到 SVE 向量再执行非临时写增加了指令；测试程序随后还会读取输出做校验，完全绕开缓存未必有利。

**决策：** 保留直接 `svst1_hor_za32` 写回。

### 4.8 失败：列分区优先遍历

**假设：** 同一列分区连续计算相邻 16 行块，可以复用重叠的输入行。

**结果：** Case 1/2 约慢 6%–7%。

**原因分析：** 理论上的纵向重叠没有转化为实际 L2 收益，反而破坏了当前连续横向扫描、线程任务分布和硬件预取行为。

**决策：** 保留行块优先、块内列分区的顺序。

### 4.9 失败：SME2 四向量加载

**假设：** 使用四向量加载可减少热循环加载指令数。

**结果：** BiSheng 明确报告该 intrinsic 需要 `sve2p1|sme2`，当前 `-mcpu=native` 不提供这些特性。

**原因分析：** 服务器支持 SME，但不等于支持 SME2。强行添加目标特性存在非法指令风险。

**决策：** 不强开 SME2，不把不可在官方节点安全运行的代码放入提交实现。

### 4.10 失败：SVE 三角边缘 + SME 中央满载区

**假设：** 当前 16 行对角映射需要 `kernelHeight + 15` 个物理行。若顶部和底部三角区域用普通 SVE 精确计算，只让 SME 处理所有 16 行均有效的中央区域，可以消除零 lane 对应的外积工作。

**实现：** 顶部 SVE 部分和按参考顺序写入 ZA；中央使用原 SME 微内核；再从 ZA 读回每行并用 SVE 追加底部贡献。补充尺寸和四个公开 Case 均 PASS，最大误差为 0。

**结果：** 四个公开 Case 仅约 `3145 / 2752 / 4027 / 5361 GFLOPS`，远慢于完整 SME 路径。

**原因分析：** 一条 FP32 `FMOPA` 能更新 16×16 个累加值。边缘虽只有部分有效 lane，但用普通 SVE 替换后，需要为每个输出行、每个核系数执行大量独立向量 FMA；精确减少的无效 FLOP 不足以抵消约数量级增加的指令数。

**决策：** 完整回退。以后若继续研究边缘，必须仍用 SME 密度组织多个边缘任务，不能简单改成逐行 SVE。

### 4.11 失败：8 列核展开

**假设：** 把核列组从 16 缩到 8，可以将连续 `EXT` 依赖链减半，并可能改善前端发射。

**结果：** Case 1/3 近似持平，Case 2 两轮均稳定下降约 12%–13%，Case 4 也没有稳定胜出。

**原因分析：** 每 16 个核系数需要处理两个组，输入向量加载和循环控制增多；缩短依赖链的收益不足以覆盖额外加载，尤其在 Case 2 的输入行跨度下更明显。

**决策：** 删除实验开关，生产实现固定使用 16 列通用展开。

### 4.12 失败：改变列任务分区数

**假设：** 中等核使用 2 或 8 个列分区、大核使用 1 或 4 个列分区，可能减少线程长尾或提高缓存复用。

**结果：** 中等核当前 4 分区优于 2 分区，8 分区没有稳定收益；NUMA 5 上大核 4 分区中位数约 `12391 GFLOPS`，当前 2 分区约 `12947 GFLOPS`，约慢 4%。

**原因分析：** 分区太少降低任务均衡，太多则让每个任务过短、增加调度与缓存流切换。宽核本身已有足够计算量，2 分区能保留更长的顺序扫描。

**决策：** 保留按核宽度选择的中核 4 分区、大核 2 分区策略。

## 6. 当前瓶颈的 AI 分析

### 6.1 16 行 SME tile 存在结构性额外物理行

一个 16 行输出 tile 需要处理：

```text
kernelHeight + 16 - 1 = kernelHeight + 15
```

个物理输入行。官方 GFLOPS 分子只统计真正的 `kernelHeight` 次卷积工作，但当前 SME 外积仍需要执行顶部和底部的部分有效外积。

将 `kernelHeight / (kernelHeight + 15)` 视为这种映射的理想有效工作比例，可得到：

| Case | kernelHeight | 有效工作比例 | 若逻辑得分达到 70%，外积路径约需达到的等效利用率 |
|---|---:|---:|---:|
| Case 1 | 39 | 72.22% | 96.92% |
| Case 2 | 41 | 73.21% | 95.61% |
| Case 3 | 55 | 78.57% | 89.09% |
| Case 4 | 81 | 84.38% | 82.96% |

这是一个用于判断方向的近似模型，不是官方硬件峰值公式。它说明：

- Case 1/2 若保持当前 16 行零填充外积结构，要达到逻辑 70% 会要求非常高的实际 SME 利用率；
- Case 3/4 已越过 70%，因为大核中额外 15 行占比更低；
- 仅靠再增加少量预取或编译参数，很难让全部 Case 同时达到 70%；
- 真正的大幅提升可能需要减少边缘外积指令，而不是只提高稳态循环速度。

### 6.2 Case 2 是当前主要短板

Case 2 当前为理论上限的 `58.61%`，达到 70% 仍需相对提升约 `19.43%`。它的 kernelHeight 与 Case 1 接近，但输出矩阵方向交换后性能更低，说明除了额外物理行外，输入行跨度、线程块形状、缓存/TLB 行为也在影响结果。

因此后续不能只以 Case 1 做微内核调优；每次候选至少要同时观察 Case 2 和 Case 4，避免只优化一种矩阵方向。

### 6.3 当前不是精度问题

最终四个公开 Case 和补充的非方核、窄输出、1×1 输出、不同线程数均为最大误差 0。当前瓶颈主要是性能组织，而不是误差预算。

不过，未来若使用多累加流、偶奇拆分或改变物理行顺序，浮点累加次序会改变，必须重新用官方 `1e-5` 阈值验证，不能假设仍为零误差。

### 6.4 距离理论上限还差多少

当前总分 `48612.1378` 距理论总上限 `72000` 还差 `23387.8622 GFLOPS`，若以当前结果为基数，达到理论总上限还需要约 `48.11%` 的相对提升。

| Case | 当前 GFLOPS | 距 18000 的绝对差值 | 达到 18000 仍需相对提升 |
|---|---:|---:|---:|
| Case 1 | 11359.5660 | 6640.4340 | 58.46% |
| Case 2 | 10550.2427 | 7449.7573 | 70.61% |
| Case 3 | 13251.6188 | 4748.3812 | 35.83% |
| Case 4 | 13450.7103 | 4549.2897 | 33.82% |

这些差值不意味着只要把某个参数再调快相同比例即可。越接近上限，剩余部分越可能来自多个瓶颈的乘积，例如有效外积比例、`FMOPA` 发射、加载供给、线程效率和写回开销。后续必须逐层拆分，而不是把 48.11% 当成一个单独瓶颈。

## 7. CONV 可优化位置的完整分析

### 7.1 数学算法和计算量

当前实现仍是完整 direct convolution，计算量为：

```text
2 × outputHeight × outputWidth × kernelHeight × kernelWidth
```

从算法层面可以考虑的方向及 AI 判断如下：

| 方向 | 可能收益 | 当前主要问题 | 判断 |
|---|---|---|---|
| Direct convolution + SME | 保持参考累加结构，硬件映射直接 | 仍有边缘外积和流水线浪费 | 当前主路线 |
| implicit GEMM | 可以复用成熟矩阵微内核 | 累加顺序变化，仍需构造滑动窗口 | 可研究，但不一定超过当前外积 |
| im2col + GEMM | GEMM 峰值可能很高 | 展开矩阵极大，内存、复制和 TLB 成本高；累加顺序改变 | 不优先 |
| FFT/overlap-save | 大 kernel 理论计算量显著下降 | FP32/FP64 变换误差很难匹配顺序 FP32 参考值的 `1e-5`；可能轻易超过官方分数上限 | 仅作为高风险研究 |
| Winograd | 小 kernel 可减少乘法 | 官方 kernel 为 39–81，不属于典型小核 | 不适合当前 Case |
| 可分离或低秩卷积 | 若 kernel 低秩可大幅降算量 | 随机稠密 kernel 通常不可分离；近似会改变结果 | 不适用 |
| 矩阵快速幂 | 对重复状态转移有效 | 卷积不计算矩阵幂 | 与本题无关 |

转换算法即使数学上更准确，也可能因为累加顺序与测试程序不同而超过绝对误差阈值。因此任何算法级替换都必须先用真实参考程序做误差验证。

### 7.2 循环组织和微内核

这是当前最直接的性能核心：

1. **输出块形状**：当前为 16×64；可比较 16×32、8×64 或混合微内核，观察 ZA 利用率与缓存供给；
2. **稳态与边缘拆分**：将全 16 行稳态块与最后不足 16 行的尾块分开，减少热循环中的谓词和通用判断；
3. **顶部/底部物理行**：研究能否减少 `kernelHeight + 15` 中额外 15 行对应的外积指令；
4. **软件流水**：提前加载下一组 kernel/input，同时执行当前组四条 `FMOPA`；
5. **多累加流**：用两组部分和减少 ZA 依赖，但会减少同时覆盖的输出列并改变累加顺序；
6. **展开宽度**：8 列和 16 列展开可能在前端指令数、`EXT` 数和寄存器压力之间产生不同平衡；
7. **指针递增**：将循环中的乘法索引进一步变成连续指针更新，检查编译器是否已自动完成；
8. **尾块专用路径**：完整 64 列、16 列尾块和不足 16 列尾部可以分别采用更精简的路径。

其中“减少额外物理行”和“提高 `FMOPA` 发射效率”最可能带来两位数提升；普通索引和尾块优化通常只能贡献较小比例。

### 7.3 数据布局和缓存

当前打包 kernel 的目的，是把跨 kernel 行的 16 个系数变为一个连续向量。仍可继续检查：

- 64/128 字节对齐是否减少跨缓存行加载；
- packed kernel 起始地址是否发生 L1 组冲突；
- kernel 打包顺序是否与实际 `physicalRow → ik` 访问完全一致；
- 是否值得为每线程复制小型 packed kernel，以避免共享缓存竞争；
- output 写预取的距离、locality 提示和每步行数；
- input、packed kernel、output 三条数据流是否同时超过 L1D 加载/写回端口能力；
- Case 2/4 的输入行跨度是否造成更多 TLB 或缓存冲突；
- 大页、内存对齐或首次触页策略是否能在不改变提交环境的前提下稳定使用。

AI 当前判断：packed kernel 最大约数百 KiB，能够放入每核 768 KiB L2，但还要和输入窗口、栈及其他数据竞争。Case 4 的 packed kernel 最大，Case 2 的矩阵方向则可能让输入行跨度和线程访问形状更不利。

### 7.4 OpenMP、线程和 NUMA

并行层可以优化：

- 行 tile 与列 partition 的数量；
- 静态连续分配、循环分配或二维线程网格；
- 38 个核心的亲和性和是否跨 CPU cluster；
- 相邻线程是否写入相邻 output cache line，造成一致性流量；
- 最后一批任务是否存在长尾负载；
- kernel 打包和正式计算之间的 barrier 成本；
- OpenMP 线程团队启动和重复调用时的运行时开销；
- NUMA 5、7、11 等节点的共享负载差异。

已证明“列分区优先”虽然看似能复用输入行，实测却慢 6%–7%。因此线程调度必须以交错 A/B 数据决定，不能只凭缓存直觉。

### 7.5 指令集和编译器

仍可研究：

- 最终热循环是否需要内联汇编来固定加载与 `FMOPA` 顺序；
- BiSheng 对 `svext_f32` 是否生成预期的单条 `EXT`；
- 四个 ZA tile 的更新是否均匀交错，避免连续依赖同一个 tile；
- 是否存在 SVE 寄存器 spill 或不必要的 ZA 保存/恢复；
- `-mcpu=native`、LTO、函数对齐和循环对齐的稳定收益；
- PGO 是否能改善分支布局，但不得把公开完整尺寸变成违规特化；
- 未来官方机器和编译器支持 SME2 时，再测试多向量加载。

普通编译参数已经不太可能单独提供 20%–70% 提升；它们应服务于汇编证据，而不是盲目组合。

### 7.6 精度预算

当前最大误差为 0，意味着尚未使用官方允许的 `1e-5` 误差空间。潜在方向包括：

- 将 kernel 列拆成两个部分和，最后相加，缩短单一累加依赖；
- 偶奇物理行使用不同累加流；
- 对多个连续 kernel 系数重新排序，以改善加载和外积调度；
- 在稳态和边缘使用不同累加顺序。

这些方法可能提高指令级并行，但风险很高：参考实现是顺序 FP32 累加，数千项求和对重排敏感。每次只改变一种重排方式，先做随机数据和四个大 Case 的最大误差扫描；只要超过 `1e-5` 就必须回退。

FP16、BF16、低秩近似和直接省略小数值目前不应使用，因为很难稳定满足误差要求。

### 7.7 测量和调优方法

要接近 100%，测量本身也必须更严格：

1. 每个候选记录源码版本、编译器、参数、NUMA、线程数和节点负载；
2. A/B 交错运行，避免先跑的版本独占较低温度或较低负载；
3. 使用 3–5 轮中位数或截尾均值；
4. 四个 Case 同时观察，不能只优化 Case 1；
5. 把正确性、打包耗时、微内核耗时和写回耗时分别分析；
6. 若性能计数器无权限，至少通过汇编静态计数和不同块形状构建间接证据；
7. 任何超过 18000 的结果先按异常处理。

### 7.8 剩余优化方向优先级

| 方向 | 潜在收益 | 实现/正确性风险 | 优先级 |
|---|---|---|---|
| SME 汇编发射和加载流水分析 | 中到高 | 中 | 最高 |
| 减少顶部/底部额外外积 | 高 | 很高 | 最高，长期核心 |
| 双累加流或重排累加 | 中到高 | 精度风险高 | 高，必须先测误差 |
| Case 2/4 缓存与 TLB 定位 | 中 | 中 | 高 |
| packed physical-row padding / L1 组冲突 | 低到中 | 低 | 中 |
| 输出预取距离搜索 | 低到中 | 低 | 中 |
| OpenMP 二维调度 | 中 | 中 | 中，已有失败样本 |
| FFT/implicit GEMM | 理论上很高 | 精度、内存和合规审查风险很高 | 研究性 |
| 更多普通编译参数 | 低 | 低 | 低 |

### 7.9 从成功和失败实验反推真实瓶颈

单看某个实验“快了或慢了”不够，真正有价值的是它对瓶颈位置提供了什么证据：

| 实验现象 | 排除或确认的假设 | AI 得出的方向性结论 |
|---|---|---|
| 立即数窗口改为滚动窗口后总分提升 17.28% | 算术量和内存数据量都没变，变化主要来自生成指令 | 前端指令数、寄存器搬运和编译器寄存器分配曾是主要瓶颈；汇编审计有实际价值 |
| 跨 16 列组携带窗口主要改善 81×81 | 小核只有 2–3 个完整组，大核有更多重复输入加载 | 大核更容易受 L1 加载供给限制；减少重复 load 比进一步缩短 `EXT` 链更重要 |
| packed kernel 64 字节对齐稳定提升 2.65% | 计算顺序完全不变，仅起始地址改变 | packed-kernel load 确实对缓存行边界敏感，缓存供给不是次要问题 |
| 8 列展开使 Case 2 慢 12%–13% | 更短的 `EXT` 依赖链没有带来收益 | 当前不是单纯的长依赖链瓶颈；额外输入加载和循环前端成本更关键 |
| SVE 精算边缘仅得到 2.75k–5.36k | 有效 FLOP 减少很多，但指令密度骤降 | 不能只追求“少算”；任何边缘优化必须保持 SME 外积级别的每指令工作量 |
| 大核 4 分区慢于 2 分区 | 更多任务没有改善长尾 | 大核计算量足够，顺序缓存局部性比更细的任务切分重要 |
| 列分区优先遍历慢 6%–7% | 相邻行输入重叠没有转化成收益 | 硬件预取、输出连续写和线程访问形状共同决定缓存效果，不能只按理论复用量排序 |

这些证据共同指向两个层次：

1. **短期瓶颈**是热循环发射和 L1/L2 数据供给，仍可能用汇编调度、地址生成、对齐和预取获得个位数到低两位数收益；
2. **长期瓶颈**是 16 行对角 SME 映射的额外物理行。它不消除，90% 在近似模型下没有空间。

### 7.10 当前微内核的结构性上限模型

当前一个 16 行输出 tile 扫描 `kernelHeight + 15` 个物理输入行，而官方得分只按 `kernelHeight` 个有效 kernel 行计算。若把 `18000 GFLOPS` 看作满载 FP32 SME 的政策理论上限，则保持当前映射、即使热循环达到 100% 满载，逻辑得分的近似上限为：

```text
结构上限 ≈ 18000 × kernelHeight / (kernelHeight + 15)
```

| Case | 当前 GFLOPS | 当前映射结构上限 | 相对结构上限的等效利用率 | 去掉额外 15 行且保持现有效率时 |
|---|---:|---:|---:|---:|
| Case 1，KH=39 | 11359.5660 | 13000.0000 | 87.38% | 15728.6298，官方上限的 87.38% |
| Case 2，KH=41 | 10550.2427 | 13178.5714 | 80.06% | 14410.0875，官方上限的 80.06% |
| Case 3，KH=55 | 13251.6188 | 14142.8571 | 93.70% | 16865.6967，官方上限的 93.70% |
| Case 4，KH=81 | 13450.7103 | 15187.5000 | 88.56% | 15941.5826，官方上限的 88.56% |
| **总计** | **48612.1378** | **55508.9286** | — | **62945.9966，官方总上限的 87.42%** |

这是性能预算模型，不是对硬件峰值的绝对证明；官方 `18000` 也可能是赛事政策上限，而非精确测得的芯片峰值。但它足以说明：

- 当前映射即使完全理想，总占比近似也只有 `77.10%`；
- Case 3 的稳态等效利用率已约 `93.70%`，继续调整普通编译参数不可能再提供 30% 收益；
- 若只消除额外 15 行、保持当前其他效率，总占比预计约 `87.42%`；
- 要达到 90%，需要“消除大部分边缘额外工作”后，再把整体稳态效率提高约 3%；
- 要接近 100%，即使消除边缘后仍需约 14% 的整体效率提升，且 Case 2 需要最明显的缓存/发射改进。

### 7.11 从五个角度冲击 90%–100%

#### A. 从 CONV 数学结构入手

当前优化利用的是 Toeplitz/滑动窗口结构：同一物理输入行可同时服务多个输出行，kernel 系数形成左向量，输入列形成右向量，从而用 `FMOPA` 更新 16×16 输出。真正需要突破的是“连续 16 个输出行的有效 kernel 区间错开 15 行”。

可研究的结构方向：

1. **跨相邻输出 row tile 合并边缘 lane**：把一个 tile 顶部或底部不足 16 个有效行的外积，与另一个 tile 在同一物理输入行上的有效输出行组合。难点是两个输出 tile 的 ZA 累加状态要同时存在，可能需要 ZA 行置换或保存/恢复；只有减少的 `FMOPA` 多于状态搬运才有价值。
2. **动态 lane 压缩的边缘 SME 微内核**：边缘阶段将当前真正有效的输出行压缩到 ZA 行，计算后再散回原输出行。它必须仍由一条 `FMOPA` 服务多个有效行，不能重走逐行 SVE 的失败路线。
3. **多 row tile 批处理**：让线程一次持有两个相邻 row tile，中央区各自满载计算，边缘区尝试共享输入和 packed kernel。潜在收益来自减少重复物理行和 kernel load，但 ZA 只有 4 个 FP32 tile，状态容量是主要约束。
4. **另一种 implicit-Toeplitz 映射**：重新选择 ZA 的行/列含义，使 16 行都表示有效的 `(outputRow, kernelRow)` 组合，最后做低成本归并。若归并需要大量水平求和或散写，则可能比现方案更慢。
5. **implicit GEMM 原型**：只构造小块 patch，不生成完整 im2col；先验证误差，再比较拷贝和 GEMM 收益。完整 im2col 会产生极大的临时矩阵，不适合这些大图和大 kernel。

数学方向的硬条件是：随机稠密 kernel 不可假设可分离、低秩或具有特殊值，不能省略乘法，也不能按四个公开尺寸返回特制路径。

#### B. 从缓存、内存和地址生成入手

当前热循环同时消费三条数据流：只读 input、只读 packed kernel、最终写 output。64 字节 packed 对齐已经证明缓存行边界会影响成绩。后续应按证据顺序研究：

1. **L1 组冲突与 packed 行步长**：虽然每次 load 已对齐，但 `kernelWidth × 64` 的行步长可能让连续 physicalRow 映射到相同缓存组。可在每个 packed physicalRow 后加入少量通用 padding，扫描 0/1/2 个 64 字节 cache line；这依赖 kernelWidth，而不是公开完整尺寸。
2. **packed 布局换序**：比较 `[physicalRow][kernelCol][lane]` 与以 16 列组为单位的布局，使 kernel load 与 input 窗口组完全同步，减少地址更新和潜在 TLB 压力。
3. **输入行对齐副本**：将 input 复制到每行 64 字节对齐、stride 为 16-float 整数倍的临时区，可避免不同行起点旋转造成的跨缓存行 load；但复制约百 MiB 输入本身计入耗时，必须先证明节省超过复制成本。
4. **输出 write-allocate 调优**：继续扫描预取距离和 locality hint。非临时写已经失败，说明输出会立即被校验读取，完全绕过缓存不是正确方向。
5. **TLB 与大页**：只能使用官方环境稳定提供且提交脚本允许的机制；不得依赖管理员配置。若无法保证 transparent huge page 行为，就不能把它作为最终必需条件。
6. **每线程 packed 副本**：理论上可减少共享只读数据的缓存竞争，但会把几百 KiB 放大 38 倍并增加打包时间，优先级较低，只在计数器显示 kernel cache miss 明显时测试。

#### C. 从 38 核、NUMA 和任务分配入手

比赛允许单 NUMA 最多 38 核，因此并行优化的目标不是增加核数，而是让 38 核在同一时刻做等量的高密度工作：

1. 为每个 task 建立估算成本：`rowCount × colBlocks × (kernelHeight + rowCount - 1) × kernelWidth`，按成本而非任务数量切分线程区间，减少最后一批不完整 row tile 的长尾；
2. 记录每线程起止时间，判断 Case 2 是否存在少数线程延迟，而不是只看总耗时；诊断代码不能进入最终计时路径；
3. 比较 `close` 和明确 CPU 列表，但必须仍只绑定一个 NUMA 节点；不得使用跨 NUMA 获得带宽；
4. kernel 打包与计算之间目前有 OpenMP barrier。可研究让每线程先打包自己即将使用的范围并直接进入计算，但必须避免其他线程尚未生成所需 packed 行的数据竞争；
5. 节点 5/7/11/13/15 只用于避开共享负载，不代表算法变快。所有 A/B 必须在同一节点交错运行。

#### D. 从 SVE/SME 指令和编译器入手

当前汇编已经显示“源代码看似少 14 条 `EXT`，实际却多 55 条 `MOV`”这类编译器效应。下一阶段必须围绕最终二进制而不是 C intrinsic 数量调优：

1. **双 kernel 寄存器软件流水**：交替使用两个 kernel 向量寄存器，让下一次 `LD1W` 与当前 4 条 `FMOPA` 重叠；当前 5 条 `EXT` 已隐藏部分 load latency，需要用汇编和计数器判断剩余空间。
2. **固定四 tile 发射顺序**：确认 `ZA0→ZA1→ZA2→ZA3` 的间隔足以覆盖同一 ZA 的累加延迟；若不足，可把下一窗口的 `EXT` 或 load 插入 tile 更新之间。
3. **减少整数地址指令**：为 packed kernel 和 input 使用递增指针，避免每个展开步重复 `add/lsl`。必须检查编译器当前是否已自动完成，避免无效源码重写。
4. **受控内联汇编微内核**：只固定完整 16×64 稳态块，尾部和通用尺寸继续使用 ACLE；这样能控制寄存器和发射顺序，同时把正确性风险限制在一个可替换内部函数。
5. **LTO/PGO**：可能改善函数边界和分支布局，但预期只有低个位数收益。PGO 的训练集必须包含多种合法尺寸，不能只训练四个公开 Case 形成变相特化。
6. **SME2**：当前 CPU 明确不支持，不能强行编译。只有未来官方节点能力检测确认后才可测试多向量加载。

#### E. 从精度预算和替代算法入手

当前误差为 0，但这不意味着可以任意重排。`1e-5` 是最终绝对误差阈值，不是每一步的误差预算。

- 双部分和、偶奇 K 拆分可缩短依赖链，但最终相加改变舍入顺序；应先在随机正负数据、不同幅值和最大 kernel 上扫描最大误差。
- BF16/FP16 会在数千次累加中放大输入量化误差，当前不应采用。
- Winograd适合小 kernel，39–81 的大 kernel 会使变换规模和误差迅速增加。
- FFT/overlap-save 可大幅降低运算复杂度，但 FP32 误差风险高；FP64 又增加变换成本和内存。若速度导致计分超过单 Case 18000，还会触发官方异常审查，因此必须先向官方确认算法替换是否符合赛题预期。
- 随机稠密 kernel 不能使用低秩、可分离或稀疏近似；近似结果即使多数元素接近，也不能保证所有元素绝对误差小于 `1e-5`。

### 7.12 分阶段到 90%–100% 的现实路线

以下收益是用于安排实验的研究预算，不是可直接相加的承诺：

| 阶段 | 目标 | 主要工作 | 预期性质 | 必须满足的退出条件 |
|---|---:|---|---|---|
| A | 总计 70% | Case 1/2 的 packed padding、预取距离、地址生成和负载长尾 | 约 3.7% 的短期增量，可能由多个小优化组成 | 四项 PASS；总分交错中位数稳定提升；单项不回退超过波动 |
| B | 总计 80% | 手工 SME 流水、Case 2 缓存/TLB 定位、稳态内核简化 | 还需约 18.5%，仅靠一个参数不够 | 汇编无 spill；多节点同方向；泛化尺寸 PASS |
| C | 总计 90% | 以 SME 密度合并边缘或重新设计 vertical mapping，消除大部分 `+15` 额外行 | 结构性重构；去掉边缘模型可到约 87.4%，再需约 3% 稳态提升 | 不能退回逐行 SVE；不能硬编码公开尺寸；误差 ≤1e-5 |
| D | 接近 100% | 消除剩余边缘、把 Case 2 等效利用率从约 80% 提高，并逼近满载发射 | 极高难度，可能需要新微内核甚至官方允许的替代算法 | 任一 Case 不超过 18000；完整计算、人工审查可解释 |

因此，AI 当前不把“再调几个预取参数”描述成 90% 方案。可信路线是：先用缓存和汇编把当前结构推近其约 77% 的模型上限，再完成保持 SME 密度的结构重构，把可达空间打开到约 87%–90%，最后才讨论逼近 100%。

## 8. 后续实验优先级

### P0：先获得性能证据

1. 为 `conv2d` 建立独立诊断 harness，只计内核调用，避免官方 benchmark 的慢速参考卷积淹没 `perf stat`；该 harness 不能替代或修改 `bench_conv.c`；
2. 对最终对齐版本重新导出汇编，逐个热块标出 `FMOPA`、kernel/input load、`EXT`、整数地址指令和分支；
3. 检查 SVE spill、ZA 保存/恢复、重复地址计算和 packed-row 步长相关指令；
4. 在有权限时分别采集 cycles、instructions、L1D/L2/TLB miss、前端/后端停顿和内存带宽；
5. 分别为 Case 1/2/4 建立画像，确认 Case 2 是 load/TLB、线程长尾还是 SME 发射问题。

本轮直接对官方程序做的全进程 `perf stat` 被参考卷积和初始化主导，无法解释微内核差异，因此不把那组计数器当成结论。这也是后续必须隔离测量的原因。

没有这些证据前继续随机调整块大小，容易把共享节点波动误判为优化。

### P1：减少额外外积工作

1. 不再采用已失败的逐行 SVE 边缘，而是先画出相邻两个 row tile 在每个全局物理输入行上的有效输出 lane；
2. 寻找能在同一次 `FMOPA` 中装满 16 个有效 lane 的配对，并计算需要同时保留多少组 ZA 累加状态；
3. 只有理论上“减少的 `FMOPA` 数量 > ZA 读写、lane 置换和额外 load”时才实现原型；
4. 评估动态 lane 压缩、跨 tile 边缘合并或新的 implicit-Toeplitz 映射；
5. 对所有改变累加顺序的候选先做误差扫描，再运行大 Case。

这是最可能突破 Case 1/2 结构性限制的方向，也是实现难度最高的方向。

### P2：稳态热循环调度

1. 尝试手写或更明确地排列双 kernel load、窗口 `EXT` 和四条 `FMOPA`，减少 load-use 与同一 ZA tile 的等待；
2. 保留已胜出的 16 列展开，重点检查整数地址指令和循环回边；
3. 在已完成 64 字节对齐的基础上扫描 packed physical-row padding，定位 L1 组冲突；
4. 测试输出预取距离，而不只是每步预取行数；
5. 比较完整 16×64 稳态块的 ACLE 与受控内联汇编版本；
6. 如果未来官方 CPU 或编译器支持 SME2，再重新验证四向量加载。

### P3：泛化和工程化

1. 增加外部批量回归脚本，随机生成合法尺寸和线程数，但不修改官方测试程序；
2. 自动记录 Git 提交、编译器版本、参数、NUMA、线程数、耗时和 GFLOPS；
3. 使用中位数或截尾均值评价 A/B，不使用单次峰值；
4. 在干净目录演练 ZIP 解压、`run.sh` 编译和全部测试。

### 下一轮建议实验矩阵

| 顺序 | 实验 | 主要验证问题 | 进入主线的最低条件 |
|---:|---|---|---|
| 1 | 隔离 `conv2d` 的计数器画像 | 官方参考实现是否掩盖了真实微内核事件 | Case 1/2/4 获得可重复的 cycles、cache/TLB 和停顿证据 |
| 2 | packed physical-row padding | 64 字节对齐后是否仍有 L1 组冲突 | 四项无明显退化，至少两个 Case 稳定提升 |
| 3 | 输出预取距离扫描 | 当前预取是否过早或过晚 | Case 2 改善且其他 Case 退化不超过波动范围 |
| 4 | 手写 SME 热循环调度 | 能否让下一 kernel load/窗口 `EXT` 与当前 `FMOPA` 更充分重叠 | 汇编无 spill，交错总分稳定提升至少约 2% |
| 5 | 加权任务切分 | Case 2 是否有线程长尾 | 每线程耗时差缩小，官方总分稳定提升至少约 1% |
| 6 | 保持 SME 密度的跨 tile 边缘合并 | 能否减少 `kernelHeight + 15` 的额外外积 | Case 1/2 明显提升，不出现大量 ZA 保存/恢复，泛化 PASS |
| 7 | 新 implicit-Toeplitz 映射 | 是否能去掉大部分边缘又保持外积密度 | 模型先证明指令数下降，再要求误差 ≤1e-5 |
| 8 | implicit GEMM 小型原型 | 变换与累加重排能否先满足误差阈值 | 只有最大误差稳定不超过 `1e-5` 才值得继续性能开发 |

“最低条件”用于防止把 0.5% 左右的共享节点随机波动当作真实优化。涉及大幅代码复杂度或累加重排的候选，应要求更高的收益才值得保留。

## 9. 能否扩展

### 9.1 当前实现已经支持

- 非固定输入高度和宽度；
- 非方输入、非方 kernel；
- 输出高度不足 16；
- 输出宽度不是 16 或 64 的整数倍；
- 不同 OpenMP 线程数；
- SME、SVE、通用 SIMD 三层编译期回退；
- kernel 打包分配失败时回退到不依赖该缓冲区的路径。

### 9.2 可以继续扩展

- 将固定 512 位路径抽象为可检测向量长度的 SME 实现；
- 按 L2 容量、核心数和 kernel 范围选择预取与列任务参数；
- 将打包、微内核和调度拆成可单独测试的内部函数；
- 在支持 SME2 的未来机器上增加经过能力检测的多向量加载；
- 为编译器升级建立独立 A/B，而不是假设新版本一定更快。

### 9.3 扩展边界

- 不得针对四个公开完整尺寸直接选择特制答案；
- 不得缓存一次调用的输出供下一次计时调用复用；
- 不得修改 `bench_conv.c` 或改变 `conv2d` 接口；
- 不得跨 NUMA 或超过 38 核；
- 不应把 `zgemm/` 中另一赛题的实现混入 CONV 提交。

## 10. 阶段目标与接近 100% 的现实判断
