## 1. 一页结论

当前实现已经从普通 C 四重循环，优化为 **38 核 OpenMP + 512 位 SVE/SME + 16×64 外积微内核**。

最新官方提交成绩如下：

| Case | GFLOPS | 单项上限占比 |
|---:|---:|---:|
| 1 | 12086.9473 | 67.15% |
| 2 | 11581.6171 | 64.34% |
| 3 | 13337.1850 | 74.10% |
| 4 | 13645.9045 | 75.81% |
| **总计** | **50651.6539** | **70.35% / 72000** |

当前排名为第 11 名。相较上一版正式成绩 `49667.4161 GFLOPS`，提升 `984.2378 GFLOPS`，约 `1.98%`。

服务器普通 DDR 多轮测试的总分中位数约为 `51296.8992 GFLOPS`，正式成绩比该中位数低约 `1.26%`，处于共享服务器实测波动区间内。

从初版到当前正式成绩：

| 阶段 | 四项总性能 | 相对初版 |
|---|---:|---:|
| 原始四重循环 | 254.3092 | 1× |
| 显式 SVE | 5833.8272 | 22.94× |
| 当前 SME 正式成绩 | **50651.6539** | **199.17×** |

最重要的结论是：**SME 外积映射是数量级提升的来源；普通预取、参数微调和片上内存无法再带来同量级收益。**

## 2. 当前代码做了什么

当前 `conv2d.c` 的主路径可以概括为：

```text
输入与原始 kernel
        ↓
把 kernel 打包成适合 SME 外积读取的 16-lane 向量
        ↓
OpenMP 将输出划分为 16 行 × 64 列任务块
        ↓
四个 ZA tile 同时累加 16 × 64 个输出元素
        ↓
SVE EXT 滑动输入窗口，减少重复加载
        ↓
谓词化处理行尾、列尾和非整块尺寸
        ↓
每个输出块只写回一次
```

### 2.1 SME 16×64 外积

SME 的 `FMOPA` 一次完成一个 16×16 FP32 外积。代码同时使用四个 ZA tile：

```text
ZA0：输出列  0-15
ZA1：输出列 16-31
ZA2：输出列 32-47
ZA3：输出列 48-63
```

kernel 的 16 个系数对应 16 个输出行，input 向量对应 16 个输出列。一条外积指令能够更新 256 个累加位置，这是相比普通 SVE 获得数量级提升的核心。

### 2.2 Kernel 打包

原始 kernel 按“物理输入行、kernel 列、16 个输出行系数”打包。每组正好为 16 个 `float`，即 64 字节：

- 与缓存行对齐；
- SME 可以连续加载一整个系数向量；
- 无效的顶部和底部 lane 填 0；
- 保持原始 `kernel row -> kernel column` 累加顺序。

### 2.3 输入滑动窗口

连续 kernel 列对应高度重叠的 input 窗口。代码用五个 SVE 向量维护 64 列输出所需的窗口，通过 `EXT` 每次向右滑动一列，只补充新进入的数据，避免为每个 kernel 列重复加载四个完整输入向量。

### 2.4 通用任务分派

实现没有判断 Case 编号或完整公开尺寸，而是依据通用工作量选择策略：

- 中小 kernel：细粒度 static 任务，减少线程收尾不均衡；
- 宽 kernel：连续列分区配合 guided 调度，兼顾负载均衡和缓存局部性；
- kernel 宽度、输出块数量和尾部长度决定预取与尾部路径；
- 不满足 SME 运行条件时回退到 SVE 或普通 C 路径。

## 3. 成功的优化

| 优化 | 得到的结果 | 成功原因 | 是否保留 |
|---|---|---|---|
| 显式 SVE 多累加器 | 从初版约 254 提升到约 5834 总分 | 消除标量依赖链，一次计算多个输出列 | 保留为回退路径 |
| SME 单 ZA 16×16 | Case 1 达到约 5.2k | 把二维卷积复用转换为矩阵外积 | 是 |
| 四 ZA 16×64 | Case 1 提升到约 9.3k | 同一 kernel 向量复用到四组输出列 | 是 |
| SVE 滑动与跨组窗口携带 | 大 kernel 获得明显收益 | 减少重叠 input 窗口加载和寄存器搬运 | 是 |
| 64 字节对齐 kernel 打包 | 多轮总分约提升 2%-3% | 每个 16-lane 系数向量与缓存行对齐 | 是 |
| Fine-static / coarse-guided 调度 | Case 1/2 和 Case 4 获得稳定改善 | 减少线程长尾，同时避免任务过碎 | 是 |
| 中小 kernel carry-tail | Case 1 多轮约提升 4%，Case 2 小幅提升 | 尾部继续复用已有窗口，只补一个新 lane | 是 |
| BiSheng `-O3 -ffast-math` 内核编译 | 热循环机器码更紧凑 | 测试程序与内核分开编译，正确性仍为 0 误差 | 是 |

这些成功优化共同形成当前正式版本，而不是依赖某一个公开 Case 的完整尺寸。

## 4. 失败的优化及原因

失败实验同样重要，因为它们说明剩余瓶颈不在哪里。

| 尝试 | 实测结果 | 失败原因 | 最终处理 |
|---|---|---|---|
| 继续增加普通 SVE 累加器和展开 | 只能小幅变化，远低于 SME | 没有改变“一条 FMA 只更新一个向量”的结构 | 停止投入 |
| 精确去掉 SME 无效行 lane | 回退约 2%-5% | 谓词与边界控制成本高于减少的无效计算 | 删除 |
| SVE2 `TBL` / `SPLICE` 构造窗口 | 接近持平或回退 | 指令更少但延迟、寄存器压力和后端停顿更高 | 删除 |
| 每列直接加载四个 input 向量 | 固定核回退约 10.9% | `LD1W` 和寄存器搬运数量显著增加 | 删除 |
| kernel-height 分带 ZA 行环 | Case 1 最好仅约 8.4k | 虽减少 8%-14% 外积，但部分和反复写回/重载更昂贵 | 删除 |
| packed-kernel 缓存分段 | 回退约 6%-10% | ZA spill/reload 流量超过 L1 复用收益 | 删除 |
| 尾部 2/4 路展开 | Case 1 持续回退 | 活跃向量过多，增加寄存器和 load 队列压力 | 删除 |
| KBLAS / KuDNN / im2col GEMM | 慢或无法满足精度 | 数据展开、通用库开销和累加顺序不适合本题 | 删除 |
| FFT / Winograd / 低秩分解 | 不适合作为通用实现 | kernel 为随机大核，且严格误差阈值限制变换顺序 | 不采用 |
| 宽 kernel carry-tail（65-96） | 81、83 宽三轮均回退 | 宽核下直接尾部加载更适合当前寄存器与缓存状态 | 删除 |

### 4.1 片上内存为何不采用

服务器 Flat 模式把约 4 GB 的 memory-only 节点暴露为独立 NUMA。单轮曾得到 `51917.3699 GFLOPS`，但多轮复测否定了其稳定性。

节点 7 的五轮公开 Case 配对测试：

| 指标 | 普通 DDR | 配对片上内存 |
|---|---:|---:|
| 总分轮次中位数 | 51296.8992 | 51022.7257 |
| 配对差值中位数 | - | **-161.0283，约 -0.31%** |

相邻非公开尺寸约提升 1.08%，但不同 Case 有升有降；节点 5、13、15 的方向也互相矛盾。说明此前 Case 4 的 14.5k 是共享环境下的单次高点，不是可泛化收益。

此外，`numactl -N 7 -m 23` 同时涉及计算 NUMA 和 memory-only NUMA 两个 ID，合规关系也未得到官方书面确认。因此当前 `run.sh` 不使用片上内存。

## 5. 当前瓶颈

### 5.1 `KH+15` 额外物理行

当前内核一次计算 16 个输出行，需要扫描 `kernelHeight + 15` 个物理输入行。评分只计算真实的 `kernelHeight` 行，因此小 kernel 的结构损失更明显：

| Case | KH | 有效计算比例 `KH/(KH+15)` | 当前映射理想上限 |
|---:|---:|---:|---:|
| 1 | 39 | 72.22% | 14051.56 |
| 2 | 41 | 73.21% | 14244.57 |
| 3 | 55 | 78.57% | 15286.86 |
| 4 | 81 | 84.38% | 16416.00 |

这解释了为什么排行榜成熟方案通常随 kernel 变大而提高 GFLOPS，也解释了为什么 Case 1/2 不能只靠预取参数达到 14.5k。

### 5.2 SME 热循环供给

热循环仍需要同时完成：

- kernel 向量加载；
- input 向量加载与 `EXT` 滑动；
- 四条 `FMOPA`；
- 地址计算和 OpenMP 任务推进；
- ZA 最终写回。

Case 1/3 已较接近当前映射的实现效率上限；Case 2/4 的后端停顿、缓存/TLB和线程长尾更加明显。

## 8. 后续优化方向

当前 70.35% 距离 80% 总分线还差 `6948.3461 GFLOPS`，距离 90% 还差 `14148.3461 GFLOPS`。后续优先级如下：

1. **完整 SME 稳态流水**：手写或内联汇编实现跨两个 kernel shift 的 load/EXT/FMOPA 双缓冲；固定核微基准先达到至少 10% 收益，再进入全 Case。
2. **输出写回重叠**：在不产生部分和、不增加输出流量的前提下，将 ZA drain 与下一 tile 准备重叠。
3. **通用多微内核分派**：依据 kernel 宽高、尾长、packed-kernel大小和输出任务数选择实现；必须在相邻非公开尺寸上同步获益。
4. **突破 `KH+15` 的新映射**：必须保持输出只写一次和原始 FP32 累加顺序；任何需要反复保存完整部分和的方案不再实现。
5. **稳定性优化**：继续记录多轮中位数和最差轮，避免把共享服务器单次峰值当成代码收益。

`70%` 只是当前阶段结果，不是终点；但 80%-90% 必须依靠新的微内核流水或数学映射，而不是继续扫描小参数。

## 9. 最终结论

- **成功主线**：OpenMP + SVE/SME 16×64 外积 + 对齐打包 + 滑动窗口 + 通用任务分派。
- **当前正式成绩**：`50651.6539 GFLOPS`，理论上限的 `70.35%`。
- **当前可信多轮水平**：普通 DDR 总分中位数约 `51296.8992 GFLOPS`。
- **已否决方向**：片上内存、分带部分和、TBL窗口、直接全加载、缓存分段、通用库替换和宽核 carry-tail。
- **提交选择**：保留当前普通 DDR 版本，不加入未经证明或存在合规疑问的实验路径。

## 10. 2026-09-01 10:48–11:28 CST：空闲 NUMA 选择与 kernel 打包缓存

本轮先确认固定节点并不可靠：节点 9 在第一次采样时较空闲，但随后被其他作业占满；同一代码在节点 7、3、9 上的波动足以掩盖低个位数优化。因此 `run.sh` 改为启动时采样普通计算 NUMA 的 CPU 负载，只选择一次节点，并让四个 Case 全程固定在该节点。仍然严格遵守单 NUMA、最多 38 核。

真正保留的代码优化是 **kernel 打包缓存**。原实现的每次 `conv2d` 调用都会重新申请缓冲区，并把同一只读 kernel 重排成 SME 所需的 16-lane 连续格式。新实现只缓存这一打包格式，不缓存 input、output 或卷积结果；每次调用都用 `memcmp` 校验 kernel 的全部字节，尺寸或内容变化就重新打包。缓存最多保留调用线程的一份权重，空间有界。

固定 NUMA 3、38 线程的两轮相邻 A/B 均值如下：

| Case | 原实现 GFLOPS | 打包缓存 GFLOPS | 可归因变化 |
|---:|---:|---:|---:|
| 1 | 12203.0676 | 12758.0572 | +554.9896 / +4.55% |
| 2 | 11648.9951 | 12184.1289 | +535.1338 / +4.59% |
| 3 | 13753.9358 | 13908.4357 | +154.4999 / +1.12% |
| 4 | 13707.4006 | 13719.7621 | +12.3615 / +0.09% |
| **总计** | **51313.3990** | **52570.3838** | **+1256.9848 / +2.45%** |

额外的 `37×39`、`43×47`、`53×57`、`79×83` kernel 尺寸全部 PASS、最大误差 0；单轮收益约为 `18.7% / 13.5% / 7.2% / 9.0%`。另用独立双实现测试在同一 kernel 地址原地修改首尾权重，缓存实现与每次重打包实现逐元素完全一致，证明内容变化能正确使缓存失效。

最终 `run.sh` 端到端重编译并自动选择 NUMA 3，得到：

| Case | GFLOPS | 18000 占比 | 校验 |
|---:|---:|---:|:---:|
| 1 | 12882.8930 | 71.57% | PASS / 0 |
| 2 | 12005.7865 | 66.70% | PASS / 0 |
| 3 | 13912.0116 | 77.29% | PASS / 0 |
| 4 | 14454.7411 | 80.30% | PASS / 0 |
| **总计** | **53255.4322** | **73.97%** | **全部 PASS** |

这是共享服务器的一轮提交路径快照，不把它冒充稳定均值；代码收益以相邻 A/B 的 `+2.45%` 为准。

本轮失败且已删除或未采用的实验：

| 尝试 | 结果 | 结论 |
|---|---:|---|
| 相邻两组 kernel 向量提前加载 | 单核中位数约 -0.37% | 增加寄存器压力，删除 |
| 静态右边缘窗口，单步少一次 `EXT` | 41 宽约 -0.07%，55 宽约 -1.65% | 指令减少但依赖和活跃寄存器增加，删除 |
| `OMP_WAIT_POLICY=active` | 反向复测中 Case 2 一轮降至约 7.6k | 共享环境下不稳定，不写入脚本 |
| 固定 NUMA 9 | 节点可从空闲迅速变为满载 | 改为启动时动态采样，不硬编码 9 |

本轮仍未达到每个 Case `+1000～2000`，更没有达到官方 90%。原因是缓存只消除调用级固定开销：Case 1/2 调用较短，因此增益约 4.5%；Case 4 的 25 ms 主要由 SME 主循环占据，缓存几乎不能改变其稳态吞吐。若要让每项再增加 1K～2K，必须产生降低实际 `FMOPA` 数或提高真实 SME 稳态吞吐的全新映射，不能靠继续添加预取或线程环境变量实现。

## 11. 2026-09-01 11:28–12:00 CST：大 packed-kernel 分组副本

### 11.1 为什么沿这个方向继续

上一节的单份打包缓存减少了重复打包，但 38 个工作线程仍共同读取同一块 packed kernel。服务器的每核 L2 为 768 KiB；Case 4 的单份 packed 权重约为：

```text
(kernelHeight + 15) × kernelWidth × 16 lane × sizeof(float)
=(81 + 15) × 81 × 16 × 4
=497664 B，约 486 KiB
```

它已占每核 L2 的大部分空间，同时还要容纳输入窗口、指令和其他运行时数据。由此提出假设：大 kernel 的瓶颈之一不是打包次数，而是所有核心读取同一组约 486 KiB 缓存行时产生的共享缓存、互连和替换压力。

本轮没有复制 input、output 或计算结果，只复制已经由原 kernel 生成的只读 packed 权重。每个线程仍执行完整卷积，累加顺序和输出写回均未改变。

### 11.2 副本数量扫描

先在 Case 4 上扫描 1、2、4、8、19、38 份，并按正反序各运行一次。关键均值如下：

| packed 副本数 | Case 4 GFLOPS | 相对 1 份 |
|---:|---:|---:|
| 1 | 13459.4346 | 基准 |
| 8 | 14158.7194 | +5.20% |
| 19 | 14930.8739 | +10.93% |
| 38 | 14950.4574 | +11.08% |

19 与 38 已近似持平。因此默认采用最多 19 份：在标准 38 线程运行中，每两个线程共享一份，避免 38 份带来的额外内存占用。Case 4 总 packed 空间约为 9.02 MiB，仍远小于输入和输出矩阵。

四个公开 Case 的完整正反序 A/B 中，只将大工作集使用 19 份的保守可归因结果为：

| 项目 | 单份 packed GFLOPS | 大工作集 19 份 GFLOPS | 变化 |
|---|---:|---:|---:|
| Case 4 | 13498.2125 | 14620.4578 | **+1122.2453 / +8.31%** |

前三项在最终门控下仍走原单份路径，故不把共享服务器中它们的随机起伏计入代码收益。该改动把本轮可归因总分从约 `51443.62` 提高到约 `52565.86 GFLOPS`，约 `+2.18%`。

### 11.3 泛化门控如何确定

最初按 `kernelWidth >= 65` 启用副本，但继续测试后发现更合理的判据是 packed 字节数。额外方核正反序 A/B 均值如下：

| 额外 kernel | 单份 GFLOPS | 19 份 GFLOPS | 变化 |
|---:|---:|---:|---:|
| 65×65 | 10631.6564 | 10834.2756 | +1.91% |
| 73×73 | 11436.6279 | 11910.1062 | +4.14% |
| 79×79 | 12371.1823 | 12815.3316 | +3.59% |

此前 53×57 的全副本测试约回退 3.16%。它的 packed 工作集约 242.25 KiB，而 65×65 已约 325 KiB。因此正式实现采用通用规则：

```text
packedBytes < 256 KiB  -> 1 份
packedBytes >= 256 KiB -> 最多 19 份，并按 OpenMP 线程号均匀映射
```

该条件只取决于 kernel 高宽形成的真实工作集，不判断输入行列组合，也不识别四个公开 Case，能够覆盖非方核和不同线程数。缓存键同时记录副本数、kernel 尺寸和完整内容；同一地址上的权重被修改时仍会立即重建。

### 11.4 被否决的扩展

为了确认小 kernel 是否也能使用较少副本，进一步扫描了 Case 1–3 的 1、2、4、8、19、38 份：

- Case 1 的 2 份在初筛中出现正值，但四轮交替复测均值约慢 1.1%；
- Case 2 没有任何副本数量稳定超过单份；
- Case 3 的 8 份初筛看似提高，随后两组 ABBA 均未胜出；
- 因此没有为公开 Case 建立独立参数表，也没有把噪声峰值写入默认分派。

这组失败说明收益不是“复制越多越快”，而只在 packed 工作集对共享缓存形成足够压力时出现。窄核复制会增加缓存占用，反而可能挤出输入窗口。

为消除运行时分支，还实验了三种生成两条常量路径的方法：

第三项是明确的正确性/运行失败，已立即撤回；两个无效果的隐藏编译参数也没有加入 `run.sh`。

### 12.5 本轮结论

- Case 2 的确存在约2.5%的“常量streaming预取”空间，但目前没有低开销、可泛化地生成两条SME worker的方法；
- 不能直接按公开 Case 或精确宽度41启用该路径；额外连续宽度扫描已经证明图像纵横结构才是更合理的判据；

### 13.2 双 worker 方案

第12节已经证明常量 streaming input prefetch 对大纵向输入有效，但把选择条件写进 physical-row 循环会抵消收益。本轮改为：

1. 用同一份 `conv2d.c` 分别编译 `conv2d_keep` 和 `conv2d_stream`；
2. 两份 worker 的差异只有 `__builtin_prefetch` 的编译期 locality 常量；
3. 由独立的 `conv2d_dispatch.c` 在进入 SME 热循环前选择一次；
4. 不强制内联 locally-streaming 函数，因此没有破坏 SME ABI，也不再触发 `Illegal instruction`；
5. 两条路径执行相同卷积、打包、累加和写回，不缓存输入或输出结果。

分派依据为通用工作集特征：

```text
inputHeight > inputWidth
且 input 工作集 >= 64 MiB
且 41 <= kernelWidth <= 64
    -> streaming-prefetch worker
否则
    -> L2-keep worker
```

该条件不判断完整公开尺寸，也不识别 Case 编号。64 MiB 门槛来自额外尺寸：约24 MiB的小纵向输入上 streaming 基本持平或略退；约80～96 MiB的纵向输入上，宽41、47、55、63均出现约1%～3%的连续收益。横向输入仍保留重叠缓存线。

## 15. 2026-09-01 14:05–14:18 CST：SME 输入窗口交错推进实验

### 15.1 假设与实现

当前每个 kernel shift 的顺序是“连续更新5个窗口，再执行4个 `FMOPA`”。理论上可以把窗口分成两组：先更新 `window0/1` 并执行 ZA0/ZA1，再更新 `window2/3` 并执行 ZA2/ZA3，最后推进 `window4`。这样希望让 `EXT` 与 ZA 指令在后端交错，隐藏窗口移位依赖。

实验通过 `CONV_SME_INTERLEAVE_WINDOWS=1` 编译一个独立 worker；默认值0保持正式路径不变。交错版本不改变 kernel load、`FMOPA` 次数、ZA tile 顺序或浮点累加顺序，仅改变非算术指令排列。

### 15.2 结果

Case 4、38线程、NUMA 7、每个进程连续调用100次，四轮 ABBA：

| worker | 平均耗时 |
|---|---:|
| 原顺序 | 24.9778 ms |
| 交错窗口 | 25.0310 ms |
| 变化 | **-0.21%** |

交错版本使用官方测试程序在额外 `512×640, 45×47` 尺寸上校验，最大误差为0、结果 `PASS`；但性能没有正向变化，反而略慢。推断原因是：当前硬件已经能够在连续 `EXT` 之间安排独立 ZA 指令，手工交错没有减少依赖；同时交错顺序增加了寄存器活跃跨度，使调度器和后端资源压力略升。

### 15.3 结论

该方向以“简单重排指令”无法获得收益，`CONV_SME_INTERLEAVE_WINDOWS` 不进入 `run.sh`。如果未来再次研究后端流水，必须改变更高层的工作单元（例如两个独立 output tile 的软件流水或跨 row tile 的输入复用），而不是继续在同一条5窗口链上调整 `EXT` 顺序。

## 16. 2026-09-01 14:20–14:39 CST：宽 kernel 输入预取专用 worker

### 16.1 动机与实验设计

性能计数器显示 Case 4 的 backend stall 明显高于 Case 1/2；它的 kernel 宽度为81，单个输出 tile 需要跨越更多输入行，原 worker 的输入预取条件（宽度不超过64）不会触发。为避免把较远预取距离施加到中等 kernel，新增第三个编译期 worker：

- `conv2d_keep`：原有 locality-2、distance=4，负责普通/中等宽度；
- `conv2d_stream`：原有 locality-0、distance=4，负责大 portrait 输入的中等宽度；
- `conv2d_wide`：仅按通用条件 `kernelWidth > 64` 分派，使用 `CONV_SME_PREFETCH_MAX_WIDTH=128`、`CONV_SME_INPUT_PREFETCH_DISTANCE=8`。

该条件是 kernel 宽度类别，不识别四个公开完整尺寸；其余计算、累加顺序、测试接口和资源限制均不变。

### 16.2 成功结果

### 16.3 失败/不保留的相关尝试

1. **packed kernel 副本间 64B padding**：单 worker 初筛一度快约2%，但四轮 ABBA 平均从约24.80ms 变为25.08ms（约-1.1%），缓存组冲突假设未被稳定验证，默认 padding 仍为0。
2. **八 ZA tile**：尝试使用 `svmopa_za32_f32_m` 的 tile 4–7 来扩大到128列输出，但毕昇 ACLE 在目标平台明确拒绝，合法范围只有0–3；因此硬件/编译器接口不支持该路线，不能作为比赛实现。
3. **按宽度关闭输出预取**：自定义 profiling harness（复用同一 output 指针）中 Case 4 有明显峰值，但它没有模拟官方每轮复制 output 的计时边界；放回正式 bench 后收益不能复现，故没有保留该候选。

### 16.4 后续方向

宽 worker 只解决了输入行提前取数的一部分问题，距离90%理论上限仍有空间。后续优先级为：

1. 在正式 bench 的 output-copy 计时边界下，对 `distance=6/8/10` 和 locality 0/1/2 做四 case ABBA，而不是依据无复制 profiling 下结论；
2. 采集宽 worker 的 L2 refill、backend stall、内存带宽，确认收益来自隐藏 DRAM 延迟而非频率波动；
3. 研究两个相邻 64 列 output tile 的软件流水/输入窗口共享，目标是在不增加 `FMOPA` 次数的情况下提高 SME 后端占用；
4. 继续保持 `kernelWidth` 类别分派、随机合法尺寸校验、单 NUMA 和最多38线程约束，避免公开 case 硬编码。

## 18. 2026-09-01 14:50–15:01 CST：5.8 万目标的内核微结构探索

### 18.1 实验结果

在远端鲲鹏节点 11、38 线程、官方测试程序下，对当前 SME 内核做了三类隔离实验，所有尺寸均 `PASS`：

| 方向 | 代表配置 | 结果 |
|---|---|---|
| Case1 窄 kernel 输入预取 | 宽度 1–40、distance=4、locality=2 | 约 +1%，不足以形成千级提升 |
| Case2 portrait 预取 | distance=6 / 8、locality=0 | distance=6 无稳定收益，distance=8 明显变慢 |
| Case3 中宽 kernel 预取 | distance=6 / 8、locality=2 | 与 distance=4 基本持平或略慢 |
| 物理行循环展开 | unroll 2 / 4 | 展开4在 Case3 下降，展开2无稳定收益 |
| packed kernel 全谓词加载 | 系数加载改用全16 lane谓词 | 各 Case 仅有噪声范围波动 |
| `CONV_SME_BLOCKS_PER_TASK` | 1 / 2 / 4 | Case2 最多约1%波动，Case3无稳定提升 |
| `OMP_PROC_BIND` | close / spread | spread 未优于 close，不能作为正式默认值 |

### 18.2 分析结论

这些实验排除了“单纯调预取距离、任务合并或循环展开即可再提高 7%”的假设。当前热循环的 L1/L2 数据复用和 16×64 ZA tile 结构已经较成熟，前三个 Case 的剩余差距更可能来自 SME 后端发射/依赖链，而不是显式缓存未命中。要从约 5.4 万稳定提升到 5.8 万（约 +7%），需要新的软件流水或内核布局，并且必须在四个 Case 的正式计时边界下验证，不能继续依赖单 Case 峰值。

### 18.3 下一阶段高收益方向

1. 设计两个相邻 output tile 的跨 tile 软件流水：在计算 tile A 的 FMOPA 时预取/准备 tile B 的输入窗口，减少每个 64 列块重新建立窗口的空隙；不能增加 ZA tile 数量，也不能改变累加顺序。
2. 对 Case1–3 分别生成通用几何类别 worker（窄宽度、portrait 中宽度、landscape 中宽度），使用编译期宏选择任务粒度和预取策略；分派条件必须基于宽度/工作集类别，不能硬编码完整公开尺寸。
3. 使用 `perf`/硬件计数器只测量 `conv2d` 区间，确认 SME pipe issue、L2 refill 和内存带宽占比，再决定是继续算力流水还是转向访存布局。
4. 若上述软件流水仍无明显收益，才评估手写 SME 汇编或调用 KBLAS；两者均需先证明支持当前 SME ABI，且不能牺牲随机尺寸泛化和 `1e-5` 校验。

当前判断：5.8 万不是通过现有参数微调就能可靠达到的目标，但仍有结构性优化空间；在新内核 A/B 结果出来前，不应把任何单次 5.4 万以上快照当成稳定成绩。

## 20. 2026-09-01 15:10–15:25 CST：架构总审查与预热复测

### 20.1 已确认的架构优点

- 分派器只在进入热循环前按通用 kernel 宽度/工作集类别选择 worker，热循环内没有 Case 分支。
- 16×64 ZA tile、16-lane kernel packing、五窗口 `svext` 滑动和 4 路 `FMOPA` 已形成稳定的计算主路径。
- packed kernel 使用线程局部缓存并验证内容变化；尾行、尾列均有谓词保护，随机合法尺寸回归通过。
- 反汇编显示编译器已将下一组 kernel `LD1W` 提前到当前组 `FMOPA`/`EXT` 之间，手工简单重排指令的收益空间很小。

### 20.2 明显缺点与影响

1. 三个中等 kernel 仍共享同一套16×64内核，仅通过预取 locality/distance 区分；Case2 portrait 和 Case3 landscape 的后端压力不同，单一 worker难以同时达到最佳。
2. 每个64列块都要重新建立五窗口并清空 ZA，跨 tile 的输入窗口无法复用；这是当前最可能带来多百分点收益、但需要重新设计任务/累加状态的地方。
3. `run.sh` 的动态 NUMA 选择只依据2秒 CPU busy率，不感知 SME 频率、内存带宽和瞬时后台任务；它能降低极端抖动，但不能保证选到最快节点。

### 20.3 外层预热复测

在 NUMA 11 对 Case1 做“无外层预热”和“先静默完整运行一次再正式计时”对照，分别约 `12768.94` 和 `12792.02 GFLOPS`，提升约 `0.18%`，处于测量噪声范围。由于额外预热会使每个 Case 的总墙钟时间翻倍，暂不写入默认 `run.sh`；保留为需要压低短 Case 抖动时的可选开关候选。

### 20.4 当前判断

目前未发现可以安全带来千级提升的简单架构缺陷。要达到5.8万以上，应优先开发“跨相邻 output tile 的输入窗口软件流水”或针对 Case1–3 的独立 tile 映射；继续调单一预取距离、线程绑定或副本数量只能获得噪声级变化。
